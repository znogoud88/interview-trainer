## Что это
**Коротко:** Next.js это фреймворк поверх React, который решает, где и когда рендерить страницу: на сервере на каждый запрос (SSR), один раз на билде (SSG), на билде с фоновым обновлением (ISR) или в браузере (CSR). Плюс роутинг, code splitting, `next/image`, API-ручки. Голый React умеет только CSR, и для SEO и быстрого первого экрана этого часто мало.

Четыре режима и когда какой:
- **SSG** (static): HTML собирается на билде, лежит на CDN, отдаётся мгновенно. Лендинги, доки, блог. Минус: данные меняются только через новый билд.
- **ISR** (incremental static regeneration): тот же статический HTML, но с `revalidate`: страница живёт N секунд или до `revalidateTag`, потом пересобирается в фоне. Каталог товаров, где тысячи страниц и пересобирать всё на каждое изменение цены нереально.
- **SSR** (dynamic): HTML рендерится на каждый запрос. Нужен, когда страница зависит от пользователя или запроса (cookies, headers, searchParams) и при этом должна индексироваться: персональная выдача, цены с учётом региона.
- **CSR**: сервер отдаёт пустую оболочку, данные тянет браузер. Личные кабинеты, админки, всё за логином, где SEO не нужно и данные приватные.

В App Router (Next 15+) режим не объявляют явно: по умолчанию маршрут статический. Как только в рендере встречается `cookies()`, `headers()`, `searchParams` или `fetch` с `cache: 'no-store'`, маршрут становится динамическим. `export const revalidate = 60` или `fetch(url, { next: { revalidate: 60 } })` превращает его в ISR.

## Пример
```tsx
// SSG: ничего динамического не читаем, отрендерится на билде
export default async function About() { return <Article /> }

// ISR: статика, но раз в минуту пересобирается в фоне
export const revalidate = 60;
export default async function Product({ params }) {
  const { id } = await params;              // в Next 15 params это Promise
  const p = await getProduct(id);
  return <Price value={p.price} />;
}

// SSR: прочитали cookie, маршрут стал динамическим
export default async function Dashboard() {
  const session = await cookies();
  return <Greeting user={session.get("user")?.value} />;
}
```

CSR в App Router это просто client component, который грузит данные через React Query или `useEffect`, или `dynamic(() => import(...), { ssr: false })` для чего-то чисто браузерного (карты, графики).

## Подводные камни
- На собесе ждут не определения, а свой пример: «лендинг у нас SSG, карточки товаров ISR с ревалидацией по вебхуку, корзина CSR». Голый пересказ четырёх слов это слабый ответ.
- Когда Next не нужен: внутренний дашборд за логином. Там SEO ноль, персональные данные всё равно грузятся на клиенте, а Node-сервер и его деплой это лишняя инфраструктура. Vite + React честнее.
- Один случайный `cookies()` в корневом layout делает весь сайт динамическим, и «статический» лендинг вдруг рендерится на каждый запрос. Смотреть на значки в выводе `next build`: ○ static, ƒ dynamic.
- SSR не бесплатен: каждый запрос это CPU на сервере и TTFB зависит от самого медленного fetch. Если данные не персональные, лучше ISR.
- ISR это не «всегда свежие данные»: первый пользователь после истечения окна получит старую страницу, свежую соберут в фоне для следующего.

## Вопросы вдогонку
- **Чем SSG отличается от ISR для пользователя?** Ничем, обе отдают готовый HTML. Разница в том, как обновляются: SSG только новым билдом, ISR по таймеру или по событию без деплоя.
- **Что делает маршрут динамическим в App Router?** Чтение `cookies()`, `headers()`, `searchParams`, `connection()`, `fetch` с `no-store`, или `export const dynamic = 'force-dynamic'`.
- **Можно ли смешать режимы на одной странице?** Да, это PPR: статическая оболочка из кеша плюс динамические куски через Suspense в одном ответе.
- **SEO и CSR несовместимы?** Google умеет исполнять JS, но медленнее и не всегда полностью. Для контента, который должен индексироваться, надёжнее отдавать HTML с сервера.
