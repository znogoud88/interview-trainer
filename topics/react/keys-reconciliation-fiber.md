## Что это
**Коротко:** После `setState` React заново вызывает компонент, получает новое дерево элементов и сравнивает его со старым (reconciliation, diffing), чтобы применить к DOM минимум правок. В списках сопоставление идёт по `key`: без стабильного ключа React путает элементы, и state «съезжает» на чужой элемент. Fiber это внутренняя архитектура (с React 16), которая делает этот процесс прерываемым и приоритизируемым.

Правила diffing, которых хватает на собес:
- Разный тип элемента (`div` стал `span`, или другой компонент) = поддерево сносится и строится заново, state внутри теряется.
- Тот же тип = обновляются только изменившиеся атрибуты/props, компонент сохраняет state, его узел переиспользуется.
- Список детей: без `key` сравнение по позиции. С `key` React находит «тот же» элемент по ключу, даже если он переехал.
- Сравнение идёт по уровням, за O(n), а не честный diff деревьев за O(n³).

Почему index как key плохо: при вставке в начало, удалении или сортировке индексы сдвигаются, и React думает, что элемент 0 это всё ещё тот же, просто с новыми props. Инпут с введённым текстом остаётся на позиции, а данные уезжают. Index допустим только для статичного списка без вставок и без state внутри элементов.

Fiber, что реально нужно знать:
- До 16 рендер был синхронным и рекурсивным: начал обход дерева, не остановишься, пока не закончишь, главный поток заблокирован. На большом дереве ввод в инпут зависал.
- Fiber: каждый компонент это узел (fiber) в связном списке, работа режется на мелкие единицы. React может остановиться, отдать браузеру кадр, продолжить, или выбросить начатое и начать заново ради более важного обновления.
- Приоритеты: ввод и клики (срочно) выше, чем переходы (`startTransition`, `useDeferredValue`) и фоновая подгрузка данных. Suspense и concurrent features существуют только благодаря Fiber.
- Две фазы: render (вычисление, прерываемая, может повторяться) и commit (запись в DOM, синхронная, один раз).

Зачем вообще это знать: рычагов управления Fiber не даёт, но без него не понять, почему компонент рендерится несколько раз, почему React может прервать рендер и начать заново, почему эффекты вызываются именно в таком порядке. Иначе «React чего-то там делает» и плывёшь по течению. Это не обязательно, но это advanced level.

## Пример
```jsx
// ❌ index как key: удалили первую строку, инпуты сохранили текст, но под чужими именами
{users.map((u, i) => <li key={i}><input defaultValue={u.name} /></li>)}

// ✅ стабильный id из данных
{users.map(u => <li key={u.id}><input defaultValue={u.name} /></li>)}
```

Тот же механизм в обратную сторону: `<UserForm key={userId} />` намеренно пересоздаёт компонент при смене пользователя, вместо сброса полей через эффект.

## Подводные камни
- `Math.random()` или `uuid()` в рендере как key это хуже index: каждый рендер всё пересоздаётся, state и фокус теряются.
- Key должен быть уникален среди соседей, не глобально. Один и тот же `id` в двух разных списках это нормально.
- Из-за прерываемой render-фазы функция компонента может вызваться и быть выброшена без коммита. Побочные эффекты в рендере (запись в ref, мутация, запрос) выполнятся лишний раз. Рендер должен быть чистым.
- Красный флаг: «Virtual DOM делает React быстрым». Нет, он делает DOM-обновления дешёвыми, а Fiber делает их прерываемыми. Быстрее ручного DOM ничего нет.

## Вопросы вдогонку
- **Что происходит после setState по шагам?** Обновление в очередь, планировщик решает приоритет, render-фаза строит новое дерево fiber (work-in-progress), diff, commit-фаза применяет правки к DOM, потом эффекты.
- **Что такое double buffering в Fiber?** Два дерева: current (то, что на экране) и work-in-progress. После коммита они меняются местами.
- **Почему нельзя делать запросы прямо в теле компонента?** Render может повториться или быть выброшен, запрос улетит несколько раз. Для этого эффекты, или `use()` с кэшированным промисом.
- **Почему diff за O(n), а не O(n³)?** Две эвристики: разные типы не сравниваются глубже, дети сопоставляются по key. Этого хватает для реальных UI.
