## Что это
**Коротко:** SOLID в React это не про классы, а про то, чтобы компоненты делали одну вещь, расширялись через composition и props, а не через `if (type === ...)`, и не хардкодили зависимости вроде API-клиента. На уровне проекта та же идея: feature-based структура, где код фичи лежит вместе и его легко найти и удалить, общий ui-кит и слой API, конвенции, которые защищает линт.

Пять принципов на React:
- **S, Single responsibility**: компонент делает одну вещь. Разбиваем UI, data fetching и бизнес-логику: `UserProfile` не делает fetch, не рендерит форму и не обрабатывает ошибки сам, а собирает `<UserData />` и `<UserForm />`. Логика уходит в хуки (`useUser`), запросы в API-слой.
- **O, Open/Closed**: можно расширять, не меняя код. `Button` с `if (type === 'primary') return ...` надо править при каждом новом варианте. `Button({ children })` или `<Button><Primary /></Button>` расширяются снаружи, через props и composition.
- **L, Liskov**: наследник подставляется вместо базового без сюрпризов. `PrimaryButton` принимает все props `Button` (`onClick`, `disabled`, `type`) и прокидывает их: `<button {...props} className="primary" />`. Если `IconButton` молча игнорирует `disabled`, там, где ждали `Button`, он ведёт себя иначе: нарушение.
- **I, Interface segregation**: не заставлять компонент принимать больше, чем ему нужно. `UserAvatar({ user })`, где `user` это объект с 40 полями, тянет зависимость от всей сущности. `UserAvatar({ name, avatarUrl })` можно использовать с чем угодно и тестировать без фикстуры на весь `User`.
- **D, Dependency inversion**: не хардкодить зависимости. Компонент, который внутри вызывает `axios.get('/api/...')`, не протестировать без сети и не переиспользовать с другим бэкендом. Зависимость приходит снаружи: через props (`onSubmit`), через хук (`useUsers()`), через context (`ApiClientProvider`), и в тестах подменяется.

Структура проекта для команды на 5 человек на 3 года (R17, Q15):
- **Feature-based**, не layer-based: `features/checkout/` с компонентами, хуками, api и тестами внутри, а не `components/`, `hooks/`, `api/` на весь проект. Структура = как команда ищет код. Удалить фичу = удалить папку.
- **Общее**: `shared/ui` (кит), `shared/api` (клиент, типы из OpenAPI), `shared/lib`. Фичи импортируют shared, shared не знает про фичи.
- **Границы защищает линт**: `eslint-plugin-boundaries` или `import/no-restricted-paths`, чтобы `features/orders` не лез во внутренности `features/users`. Публичный API фичи через `index.ts`.
- Конвенции (именование, где лежат тесты, формат ошибок API) записаны и проверяются в CI, а не живут в голове тимлида.

## Пример
```jsx
// ❌ D нарушен: компонент знает про транспорт, тест требует мок axios
function UserList() {
  const [users, setUsers] = useState([]);
  useEffect(() => { axios.get("/api/users").then(r => setUsers(r.data)); }, []);
  ...
}

// ✅ зависимость снаружи: хук инкапсулирует запрос, компонент только рендерит
function UserList() {
  const { data: users, isPending } = useUsers();   // внутри React Query + shared/api
  ...
}
// в тесте: мок useUsers или MSW на уровне сети, компонент не трогаем
```

## Подводные камни
- SOLID как карго-культ: абстракция ради абстракции, `AbstractButtonFactory`. Принцип применяют, когда есть реальная вторая реализация или реальный тест, которому мешает зависимость.
- Layer-based структура на старте кажется чище, но через год `components/` это 300 файлов, и чтобы понять фичу, надо открыть 5 папок.
- FSD (Feature-Sliced Design) это готовая версия feature-based с жёсткими слоями. Полезно знать, но не обязательно внедрять целиком: часто хватает `features/` + `shared/` + `app/`.
- Красный флаг на собесе: пересказ SOLID по учебнику про классы, без примера, как это выглядит в компоненте. Senior-ответ: пример с `if (type === ...)` и как его заменила composition.

## Вопросы вдогонку
- **Как SRP связан с размером компонента?** Не строками, а причинами меняться: если компонент правят и при смене дизайна, и при смене API, он делает две вещи.
- **Composition vs props-конфиг?** Пропс-монстр с 20 флагами это нарушение O: каждый новый кейс = правка внутри. Слоты и `children` расширяются снаружи.
- **Как внедрять зависимости в React без DI-контейнера?** Context для клиентов и сервисов, хуки как фасады, props для колбэков. В тестах подмена провайдера или MSW.
- **Что делать, когда две фичи хотят общий код?** Вынести в `shared` или в `entities`, а не импортировать друг друга напрямую: иначе циклы и склейка.
