## Что это
**Коротко:** Состояние бывает разных типов, и у каждого свой дом. Серверные данные живут в кэше запросов (React Query/SWR), UI-состояние как можно локальнее, шарабельное (фильтры, страница, выбранный таб) в URL, и только то, что реально нужно всему приложению, в глобальном сторе. «Всё в Redux» это не архитектура, а привычка из 2019.

Иерархия для клиентского state, снизу вверх:
1. **Локально** в `useState`/`useReducer`. Дефолт. Открыт ли дропдаун, значение инпута.
2. **Поднять к ближайшему общему родителю** (lift state up), если нужно двум соседям.
3. **Context**, если нужно многим компонентам поддерева и меняется редко: тема, текущий юзер, локаль. Context это DI, а не стейт-менеджер: при любом изменении value ререндерятся все потребители.
4. **Глобальный стор** (zustand, jotai, Redux Toolkit), если состояние глобальное, меняется часто и читается из многих мест: корзина, уведомления, состояние плеера. Селекторы дают точечную подписку.

Типы state, которые нельзя смешивать:
- **Серверный**: пришёл по API, у него есть «устарел ли», «грузится ли», «ошибка ли». Это кэш, не state. React Query/SWR, loader роутера или RSC.
- **Клиентский UI**: то, чего нет на сервере. Локально или стор.
- **URL**: то, что нужно шарить ссылкой или восстанавливать по F5: фильтры, пагинация, открытая модалка с id. `useSearchParams` и есть стейт-менеджер для этого.
- **Формы**: своя история, React Hook Form держит их вне ререндеров.

## Пример
Страница каталога: список товаров приходит с сервера (React Query, ключ `['products', filters]`), фильтры и номер страницы лежат в URL (ссылку можно отправить коллеге), раскрыт ли блок «Подробнее» это `useState` внутри карточки, а корзина в zustand, потому что её читают хедер, карточка и чекаут.

```jsx
// ❌ серверные данные в сторе: руками loading/error, нет инвалидации, дубли сущностей
dispatch(fetchProducts()); const products = useSelector(s => s.products.list);

// ✅ серверные данные в кэше запросов, фильтры в URL
const [params] = useSearchParams();
const { data, isPending } = useQuery({ queryKey: ["products", params.toString()], queryFn: ... });
```

## Подводные камни
- Серверные данные в Redux это самая частая ошибка: пишешь руками loading/error/refetch, кэш устаревает, одна сущность лежит в трёх слайсах в разном состоянии. Это именно та боль, под которую сделали React Query.
- Context для часто меняющегося (положение мыши, значение инпута) кладёт всё поддерево. Разбивать по частоте или брать стор.
- Дублирование: тот же `userId` в URL, в сторе и в локальном state. Два источника правды разойдутся. Один владелец, остальные читают.
- Поднимать state «на всякий случай» на уровень страницы: см. карточку про лишние ререндеры.
- Красный флаг: «мы всё храним в Redux, так проще найти». Ответ middle+: по типу данных, у каждого свой дом.

## Вопросы вдогонку
- **Когда Redux всё-таки уместен?** Сложное клиентское состояние с многими писателями, нужна трассировка (devtools, time travel), большая команда с нужными конвенциями. RTK, а не голый Redux.
- **Context или zustand?** Context для редко меняющихся значений и DI. Zustand, когда нужны селекторы и частые обновления без ререндера всего дерева.
- **Что класть в URL, а что нет?** В URL: то, что должно пережить F5 и шариться. Не в URL: чувствительное, огромное, чисто временное (hover, открытый тултип).
- **Как серверный state связан с формами?** Форма берёт `defaultValues` из серверных данных, после мутации инвалидирует запрос. Не копировать ответ сервера в state «насовсем».
