## Что это
**Коротко:** В большом приложении три разных вида состояния, и у каждого свой дом. Серверные данные это кеш, им управляет TanStack Query или SWR. UI-состояние (открыта модалка, шаг визарда) живёт локально или в лёгком сторе. Всё, чем нужно поделиться ссылкой (фильтры, страница, таб), живёт в URL. Большинство «странных багов со стейтом» это когда один вид положили в дом другого.

**BFF (backend-for-frontend)** это тонкий серверный слой под конкретный UI: агрегирует несколько сервисов, формирует данные под экран, прячет чужие API и секреты. Владеет им фронтовая команда, потому что он меняется вместе с экранами. Когда оправдан:
- chatty API: экран собирается из шести запросов, BFF отдаёт один
- разные клиенты (web, mobile, TV) хотят разную форму данных от одних сервисов
- нужно спрятать токены к сторонним API, нормализовать legacy-ответы, сделать SSR-friendly эндпоинт

Технически это Next.js route handlers, Node-сервис на Fastify/NestJS, GraphQL-гейтвей или edge functions. На фронте BFF лечит фронтовый N+1 и убирает склейку данных из компонентов.

Три дома для состояния:
- **Server cache**: TanStack Query, SWR, RTK Query, Apollo. Ключ запроса, staleTime, инвалидация после мутации, retry, dedupe. Это не стор, это кеш с временем жизни.
- **Client state**: `useState`/`useReducer` локально; Zustand, Jotai, Redux для того, что шарится между далёкими компонентами. Тут живёт только то, чего нет на сервере.
- **URL state**: `searchParams` роутера или библиотека вроде nuqs. Фильтры, сортировка, пагинация, открытая вкладка. Даёт шаринг ссылкой, back/forward, deep links, восстановление после F5.

## Пример
```tsx
// ❌ ответ API в Redux: ручной кеш, loading-флаги, никто не знает, когда данные протухли
dispatch(fetchOrders(filters)); // + slice + thunk + selectors на каждую сущность
const { orders, loading } = useSelector((s) => s.orders);

// ✅ каждому своё
const [filters, setFilters] = useQueryStates(ordersFilters);   // URL: ?status=paid&page=2
const { data, isPending } = useQuery({                          // server cache
  queryKey: ["orders", filters],
  queryFn: () => bff.getOrders(filters),                        // BFF: заказы + клиенты + статусы одним ответом
  staleTime: 30_000,
});
const [selectedId, setSelectedId] = useState<string | null>(null); // UI state
```

## Подводные камни
- BFF не оправдан, когда клиент один и бэкенд готов отдавать данные под экран: это лишний деплой, лишний hop и ещё одна точка отказа.
- BFF обрастает бизнес-логикой и становится вторым бэкендом. Правило: агрегация и формат, не правила домена.
- Server cache в глобальном сторе: дублируешь то, что библиотека делает лучше (dedupe, фоновый refetch, GC). Красный флаг: «храним ответы API в Redux», если это не RTK Query.
- URL state без валидации: `?page=abc` должен превращаться в дефолт, а не в краш. Zod на парсинг параметров.
- Не всё в URL: токены, большие объекты, транзиентное UI-состояние там не нужны.
- Смешение: фильтры в сторе, пользователь шлёт ссылку коллеге, тот видит другое. Или фильтр в URL, а данные в сторе и не перезапрашиваются при смене URL.

## Вопросы вдогонку
- **GraphQL это BFF?** Может им быть: один гейтвей, клиент выбирает поля. Но GraphQL это формат запроса, а BFF это назначение и владение слоем. Бывают REST BFF и GraphQL без BFF.
- **Как инвалидировать server cache после мутации?** `queryClient.invalidateQueries({ queryKey: ["orders"] })` в `onSuccess`, или optimistic update с откатом при ошибке.
- **Зачем Redux, если есть TanStack Query?** Для сложного клиентского состояния с историей и middleware: редакторы, канвасы, undo/redo. В CRUD-приложении часто хватает Query + URL + useState.
- **Server Components меняют картину?** Часть server cache уходит на сервер, компонент просто читает данные. Но клиентские мутации, фильтры в URL и UI-состояние остаются теми же тремя домами.
