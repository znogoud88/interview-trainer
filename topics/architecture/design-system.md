## Что это
**Коротко:** Дизайн-система это не папка с кнопками. Это токены (цвета, отступы, типографика) плюс компоненты плюс правила использования плюс процесс: как добавить новое, кто ревьюит, как доехать до потребителей. Библиотека компонентов это только кодовая часть системы.

Из чего состоит:
- **Токены**: единственный источник правды для дизайна и кода. Figma Variables -> экспорт в JSON (Tokens Studio, Style Dictionary) -> CSS-переменные и TS-константы. Дизайнер меняет primary-цвет, код получает новое значение без ручной правки.
- **Компоненты**: с продуманным API и a11y из коробки.
- **Витрина и документация**: Storybook как живой каталог со всеми состояниями, плюс гайды «когда Modal, а когда Drawer».
- **Процесс**: контрибуция, ревью, релизы, деприкации.

Самая частая проблема это drift: команды копируют `Button` к себе и правят под свой кейс, через год десять кнопок. Причина почти всегда в том, что компонент негибкий или контрибуция болезненная. Лечение через удобство, а не запреты:
- Composition вместо пропсов-монстров: `<Dialog><Dialog.Title/><Dialog.Body/></Dialog>` вместо `<Dialog titleIcon size footerButtons ...>`. Headless-подход (Radix, React Aria, Base UI) даёт поведение, внешний вид подстраивается.
- Лёгкая контрибуция: шаблон компонента, PR за день, а не через комитет.
- Линт против локальных копий: `no-restricted-imports` на `@mui/material` напрямую, если есть свой `@acme/ui`.
- Visual regression (Chromatic, Percy, Playwright screenshots) ловит сломанный внешний вид на каждом изменении.

## Пример
Релиз через changesets в монорепе:
```
pnpm changeset            # разработчик в PR описывает изменение
# -> "@acme/ui: minor. Button: добавлен size='xs'"
pnpm changeset version    # CI на main бампит версии по semver, пишет CHANGELOG
pnpm changeset publish
```

Breaking change, например переименовать `variant="ghost"` в `variant="subtle"`:
1. В 2.x оставить оба, старый пометить `@deprecated` в типах и писать `console.warn` в dev.
2. Дать codemod или хотя бы инструкцию миграции в changelog.
3. Убрать старый в 3.0. Потребители обновляют мажор осознанно, когда готовы.

## Подводные камни
- Semver честно: всё, что может сломать потребителя (убрали проп, поменяли DOM-структуру, на которую завязаны стили или тесты), это мажор. «Мелкая правка» в minor ломает чужой прод.
- Deprecation без миграционного периода равна breaking change. Хотя бы один мажор overlap.
- Дизайн-система без владельца умирает: нужна команда или хотя бы выделенные люди с процентом времени.
- Visual regression даёт шум от антиалиасинга и шрифтов. Нужны пороги и дисциплина обновления эталонов.
- Красный флаг: «дизайн-система это наш Storybook». Нет токенов, нет процесса, нет связи с Figma: это компонентная библиотека.

## Вопросы вдогонку
- **Как синхронизировать токены между Figma и кодом?** Figma Variables или Tokens Studio экспортируют JSON, Style Dictionary генерирует CSS-переменные, SCSS, TS. Пайплайн в CI.
- **Продуктовой команде нужен компонент, которого нет в DS. Что делать?** Сначала локально в приложении. Когда появляется второй потребитель, поднимать в систему. Не всё должно жить в DS с первого дня.
- **Как потребители узнают о breaking changes?** CHANGELOG из changesets, deprecation warnings в dev, Renovate/Dependabot PR со ссылкой на миграцию.
- **Headless UI или готовая библиотека вроде MUI?** Headless, когда дизайн свой и важен контроль. MUI/Ant, когда нужно быстро и дизайн не главное. Часто берут Radix/React Aria и оборачивают в свои токены.
