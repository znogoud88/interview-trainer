## Что это
**Коротко:** Структура папок это ответ на вопрос «как команда ищет код». Layer-based (все компоненты в `components/`, все хуки в `hooks/`) работает до пары десятков экранов, потом расползается: чтобы понять фичу, бегаешь по пяти папкам. Feature-based кладёт всё про фичу рядом: компонент, хуки, api, тесты. Фичу легко найти и легко удалить целиком.

Как растить приложение, чтобы билды и команды не тормозили:
- **Code splitting по роутам**: `React.lazy` / `import()` на уровне страницы, роутер и Next.js делают это из коробки. Тяжёлые зоны (графики, редакторы, PDF) лениво, не в initial bundle.
- **Монорепа с пакетами по доменам**: когда фича вырастает, она становится пакетом `packages/checkout` со своим публичным API. CI через affected собирает и тестирует только затронутое.
- **Организационно**: владение зонами (CODEOWNERS), каждая команда отвечает за свои feature-папки или пакеты, `shared` ревьюит платформенная команда.

ADR (Architecture Decision Record) это короткий markdown на одно решение: контекст (что было и что мешало), варианты, решение, последствия (что получаем и чем платим). Через год никто не помнит, почему выбрали Zustand вместо Redux или почему две системы форм. ADR помнит, и новичок читает историю решений вместо археологии в git blame.

## Пример
```
src/
  app/                 # роутинг, провайдеры, layout
  features/
    checkout/
      api/             # запросы и типы ответов
      components/      # CheckoutForm, Summary
      hooks/           # useCheckout
      index.ts         # публичный API фичи
    catalog/
  shared/
    ui/                # кнопка, инпут
    lib/               # fetch-обёртка, форматтеры
```
Правило импортов: `features/*` импортит `shared`, но не другую фичу напрямую (только через её `index.ts`, а лучше склеивать фичи на уровне `app`). Защищается `eslint-plugin-boundaries` или `no-restricted-imports`.

ADR `docs/adr/0007-server-state-tanstack-query.md`:
```
# 7. Серверное состояние через TanStack Query
Status: accepted, 2026-03
Context: 40% багов в Redux связаны с ручным кешированием ответов API, дублирующие thunks.
Decision: серверные данные только через TanStack Query. Redux остаётся для UI-состояния.
Consequences: два подхода живут параллельно 2-3 квартала; lint-запрет на новые createAsyncThunk.
```

## Подводные камни
- Feature-based без правила границ превращается в layer-based с лишним уровнем: фичи импортят друг друга напрямую, и всё связано со всем.
- Деление на фичи по экрану, а не по домену. «Профиль» и «настройки» могут быть одной фичей `account`, а «корзина» живёт на пяти экранах.
- FSD (Feature-Sliced Design) это формализованный вариант со слоями app/pages/widgets/features/entities/shared. Знать полезно, но на собесе важнее объяснить принцип, чем назвать методологию.
- ADR как бюрократия умирает: шаблон на три страницы никто не заполняет. Пишется только то, про что потом спросят «почему так», полстраницы, рядом с кодом, через обычный PR.
- Красный флаг: «структуру задал Next при создании, так и живём» на проекте в 500 файлов.

## Вопросы вдогонку
- **Когда переходить с layer на feature?** Когда для одной задачи регулярно открываешь 4+ папок или когда удалить фичу значит искать её хвосты по всему проекту.
- **Как делить, если команды не по доменам?** Сначала организация: структура кода по закону Конвея повторяет структуру команд. Иначе будет красивая папка `features/`, которую все правят одновременно.
- **Где хранить ADR и в каком формате?** В репозитории, `docs/adr/NNNN-title.md`, шаблон Nygard: context, decision, consequences, status. Статус может быть superseded со ссылкой на новый.
- **Чем ADR отличается от RFC?** RFC это обсуждение до решения, ADR фиксирует результат. Часто принятый RFC сворачивается в ADR.
