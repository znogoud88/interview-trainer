## Что это
**Коротко:** Микрофронтенды это когда один UI собран из частей, которые разные команды разрабатывают и деплоят независимо. Решают они организационную проблему, а не техническую: десять команд не могут ждать общего релиза монолита. Цена: сложность, дубли зависимостей, матрица версий.

Как склеить части в рантайме:
- **Module Federation** (webpack 5, сейчас Module Federation 2.0 с плагинами для webpack, Rspack и Vite): host-приложение в рантайме подгружает `remoteEntry.js` удалённого модуля, тот экспонирует компоненты через `exposes`. Общие зависимости описываются в `shared`.
- Альтернативы: iframe (максимальная изоляция, плохой UX), web components, single-spa как оркестратор, build-time интеграция через npm-пакеты (это уже не совсем микрофронтенды, потому что деплой общий).

Три вещи, которые надо уметь объяснить:
- **Версии фреймворка**: React в `shared` обязательно `singleton: true`. Два инстанса React на странице = сломанные хуки и контекст, потому что хуки привязаны к своей копии React. Если команды на разных мажорах React, singleton не спасёт: нужны адаптеры/обёртки и поэтапный апгрейд. Эта боль и есть детектор реального опыта.
- **Коммуникация**: события (CustomEvent на window или своя шина) и URL как контракт. Общий Redux-стор на всех = склеили монолит обратно, только распределённый.
- **Стили**: CSS Modules с хешами, префиксы, shadow DOM. Общие дизайн-токены при изолированных стилях. Утечка глобального CSS из одного модуля в другой это классический инцидент.

## Пример
```js
// webpack.config.js хоста
new ModuleFederationPlugin({
  name: "shell",
  remotes: { checkout: "checkout@https://cdn.site.com/checkout/remoteEntry.js" },
  shared: {
    react: { singleton: true, requiredVersion: "^19.0.0" },
    "react-dom": { singleton: true, requiredVersion: "^19.0.0" },
  },
});

// в коде хоста: подгружается в рантайме, а не на сборке
const CheckoutPage = React.lazy(() => import("checkout/CheckoutPage"));
```

Ситуация из жизни: команда checkout задеплоила новую версию в пятницу, QA тестировал shell с прошлой. В проде встретилась комбинация, которую никто не видел. Лечится version pinning на стендах, видимостью версий модулей в UI и логах, контрактными тестами и E2E-смоуком на интеграцию при каждом деплое любого модуля.

## Подводные камни
- Самое важное для сеньора: знать, когда это неправильный выбор. Одна команда, один продукт, один релизный цикл: микрофронтенды не окупаются. Монолит с хорошими модульными границами (монорепа, code splitting) почти всегда проще.
- Дубли: каждый модуль тянет свой lodash/dayjs, бандл пухнет. `shared` помогает, но требует дисциплины версий.
- `singleton` без `requiredVersion` молча берёт ту версию, что загрузилась первой. Проблема всплывает в проде, а не в CI.
- Минимум общего состояния. Если модулям нужно постоянно обмениваться данными, границы нарезаны неправильно.
- Красный флаг: «микрофронтенды это современно, поэтому берём». Правильный ответ начинается с «у нас N команд, которым мешает общий релиз».

## Вопросы вдогонку
- **Чем Module Federation отличается от npm-пакета с компонентом?** Пакет интегрируется на сборке, обновление требует пересборки хоста. MF подгружает в рантайме, деплой модуля независим.
- **Как шарить авторизацию между модулями?** Сессия в shell, модулям отдаётся через событие или минимальный контракт. Проще всего HttpOnly cookie, которую все запросы видят сами.
- **Как делать роутинг?** Shell владеет верхнеуровневыми роутами, каждый модуль своими вложенными. URL это публичный контракт, менять его как API: с совместимостью.
- **Что с SSR?** Сложно: у MF 2.0 поддержка SSR есть, но большинство микрофронтендов client-side. Если SSR критичен, часто выбирают монорепу вместо MF.
