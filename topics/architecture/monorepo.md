## Что это
**Коротко:** Монорепа это один git-репозиторий на несколько приложений и библиотек. Главный плюс: общий код (ui-кит, конфиги, utils) лежит рядом, изменение в библиотеке и во всех её потребителях делается одним атомарным PR, нет версионного ада между внутренними пакетами. Минусы: тяжёлый CI без affected и кеша, и нужна дисциплина границ.

Инструменты:
- **pnpm workspaces** (или npm/yarn workspaces): базовый уровень, пакеты линкуются друг на друга через `workspace:*`.
- **Turborepo**: оркестратор задач поверх workspaces, кеш сборок локально и удалённо, запуск только затронутых пакетов.
- **Nx**: то же плюс граф проектов, генераторы, `nx affected`, правила границ модулей.

Структура:
- `apps/*`: то, что деплоится (web, admin, mobile). Приложения не импортят друг друга.
- `packages/*` (или `libs/*`): то, что шарится: `ui`, `utils`, `api-client`, `config` (eslint, tsconfig), `types`.
- Правило направления: apps -> packages, packages -> более базовые packages. Никогда наоборот.

Границы защищаются линтом, а не договорённостью: `@nx/enforce-module-boundaries` с тегами, `eslint-plugin-boundaries`, `dependency-cruiser`. Плюс поле `exports` в package.json, чтобы снаружи был доступен только публичный API пакета, а не глубокие пути.

## Пример
```
repo/
  apps/
    web/          # Next.js, импортит @acme/ui, @acme/api-client
    admin/        # Vite, импортит @acme/ui
  packages/
    ui/           # кнопки, инпуты; зависит только от tokens
    tokens/       # цвета, отступы
    api-client/   # типизированные запросы; зависит от types
    types/
    eslint-config/
    tsconfig/
```

Circular dependency тут выглядит так: `ui` импортит хелпер даты из `utils`, а кто-то в `utils` добавил `formatPrice`, который тянет компонент `Price` из `ui`. Сборка иногда проходит, но в рантайме импорт оказывается `undefined`, потому что модуль ещё не доинициализирован. Чинится выносом общего в третий пакет (`format`), от которого зависят оба.

## Подводные камни
- Без affected и кеша монорепа убивает CI: каждый PR пересобирает всё. `turbo run build --filter=...[origin/main]` или `nx affected -t test` нужны с первого дня.
- Circular deps ловить в CI: `madge --circular src/`, `dpdm`, `import/no-cycle` в eslint. Руками их не видно, пока не сломается tree-shaking, HMR или не вылезет `undefined` при импорте.
- Пакет-помойка (`common`, `utils` на 200 файлов) это та же проблема, что layer-based структура: все зависят от всего. Дробить по смыслу.
- Монорепа не равно монолит: деплой приложений всё ещё независимый. И не равно микрофронтенды: это организация кода, а не рантайма.
- Красный флаг: «монорепа, потому что модно». Одно приложение и ноль шареного кода: это лишний слой.

## Вопросы вдогонку
- **Nx или Turborepo?** Turborepo проще и легче, хватает большинству. Nx мощнее: граф, генераторы, правила границ, но больше магии и конфигурации.
- **Как версионировать внутренние пакеты?** Чаще никак: `workspace:*`, всё живёт на одной версии. Semver нужен только тому, что публикуется наружу.
- **Как монорепа влияет на code review?** PR может трогать пять пакетов. Нужны CODEOWNERS на папки и affected-тесты, чтобы ревьюер видел, что реально затронуто.
- **Что такое hoisting и чем он опасен?** Менеджер пакетов поднимает зависимости в корневой node_modules, и пакет может использовать то, что не объявил. pnpm строгий, поэтому ловит это раньше.
