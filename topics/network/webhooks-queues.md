## Что это
**Коротко:** Вебхук это обратное направление: не ты зовёшь API, а сервис (Stripe, GitHub) зовёт тебя HTTP-запросом при событии. Очередь (SQS, RabbitMQ, Kafka) это тот же принцип внутри системы: приняли запрос, положили сообщение, воркер разгребает асинхронно. Общее у них гарантия at-least-once: сообщение придёт минимум раз, значит может прийти дважды, поэтому обработчик обязан быть идемпотентным.

Требования к приёмнику вебхука:
- **Проверка подписи**: отправитель подписывает тело HMAC-ом с общим секретом (`Stripe-Signature`, `X-Hub-Signature-256`), ты считаешь HMAC от сырого тела и сравниваешь constant-time. Без этого любой пришлёт «платёж прошёл». Timestamp в подписи защищает от replay.
- **Быстрый ответ**: отдать 200 за секунды, обработку в очередь или фон. Иначе отправитель считает доставку неудачной и шлёт повтор, а у тебя уже половина обработалась.
- **Идемпотентность**: придёт дважды (ретрай отправителя, сетевой сбой после твоего 200). По `event.id` храним «обработано» и повтор скипаем.

Очереди концептуально:
- **RabbitMQ**: классическая очередь, роутинг через exchange, задачи для воркеров, сообщение после ack удаляется.
- **Kafka**: лог событий с партициями, сообщения не удаляются, consumer group хранит offset, можно replay. Порядок гарантирован внутри партиции (ключ = сущность). Это стриминг, а не очередь задач.
- **SQS / Service Bus / Pub/Sub**: облачные managed-очереди, концепции 1:1, меняются только названия.

Как не потерять и не задвоить:
- **Outbox pattern**: событие пишем в таблицу outbox в той же транзакции, что и данные; отдельный процессор читает outbox и публикует в брокер. Иначе «БД записали, брокер упал» или наоборот, и данные с событиями разъехались.
- **Idempotency keys**: продюсер даёт операции ключ (uuid, `event.id`), консьюмер хранит обработанные ключи (Redis с TTL или таблица) и на повтор отдаёт тот же результат или скипает.
- **DLQ (dead letter queue)**: сообщение, которое N ретраев не пережило (ядовитое: кривой JSON, баг обработчика), уходит в отдельную очередь. Иначе оно бесконечно ретраится и блокирует остальных. DLQ мониторится и разбирается руками.

## Пример
```js
// приёмник вебхука: подпись -> быстрый 200 -> идемпотентная обработка в фоне
app.post("/webhooks/stripe", express.raw({ type: "application/json" }), async (req, res) => {
  const event = stripe.webhooks.constructEvent(req.body, req.headers["stripe-signature"], SECRET); // бросит, если подпись не сошлась
  const fresh = await redis.set(`webhook:${event.id}`, 1, { NX: true, EX: 7 * 86400 });
  if (fresh) await queue.add("stripe-event", event);   // дубль: ключ уже есть, молча отвечаем 200
  res.sendStatus(200);
});

// воркер: статус-машина, а не "прибавить"
// ✅ UPDATE orders SET status='paid' WHERE id=$1 AND status='pending'   (повтор ничего не меняет)
// ❌ UPDATE accounts SET balance = balance + $1                          (повтор задваивает)
```

## Подводные камни
- TTL ключа дедупликации короче окна ретраев отправителя (Stripe ретраит до 3 дней): через неделю дубль пройдёт.
- Пометить ключ «обработано» до самой обработки: воркер упал посередине, повтор скипнули, событие потеряно. Правильно: атомарно обрабатывать и помечать (транзакция), или помечать после и терпеть повтор, который идемпотентен.
- Ретраи без DLQ: одно ядовитое сообщение, и очередь встала. DLQ без мониторинга: события тихо копятся месяцами.
- Проверять подпись на распарсенном JSON, а не на сыром теле: сериализация меняет байты, подпись не сойдётся. Нужно сырое тело.
- Для фронта это значит: действие ≠ мгновенный результат. UI показывает «processing», результат приходит через push или polling статуса, а не в ответе на POST.
- Exactly-once в распределённой системе это почти всегда at-least-once плюс идемпотентность, а не магия брокера. Кто это проговаривает, тему понимает.

## Вопросы вдогонку
- **Чем вебхук отличается от polling чужого API?** Push вместо pull: нет лишних запросов и задержки, но нужен публичный эндпоинт, подпись и идемпотентность.
- **Твой сервер лежал час, вебхуки не дошли. Что делать?** Отправители ретраят, но на всякий случай нужна периодическая сверка (reconciliation) по API: вытянуть события за период и дообработать.
- **Kafka или RabbitMQ для фоновых задач?** RabbitMQ: задачи, ack, роутинг. Kafka: стриминг событий, replay, несколько независимых консьюмеров одного лога.
- **Зачем outbox, если брокер надёжный?** Проблема не в брокере, а в двух записях без общей транзакции (БД и брокер). Outbox делает публикацию частью транзакции БД.
