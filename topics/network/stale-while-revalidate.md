## Что это
**Коротко:** stale-while-revalidate (SWR) это «отдай старое мгновенно, обнови в фоне, следующий получит свежее». Юзер никогда не ждёт пересчёта, а данные отстают максимум на один запрос. Паттерн один и тот же на всех уровнях: HTTP-заголовок, ISR в Next, React Query и SWR на клиенте. Понимание переносится между слоями.

Механика в три шага:
1. Запрос пришёл, в кэше есть значение, но оно уже «протухло» (прошёл staleTime / max-age).
2. Отдаём протухшее сразу, без ожидания.
3. Параллельно в фоне дёргаем источник и обновляем кэш. Следующий запрос получает свежее.
Если значение протухло сильнее, чем разрешено (вышло окно stale-while-revalidate), ждём как при обычном промахе.

Где встречается:
- **HTTP**: `Cache-Control: max-age=60, stale-while-revalidate=300`. Минуту ответ свежий, ещё 5 минут кэш отдаёт старое и тихо ревалидирует. Рядом `stale-if-error`: отдавать старое, если origin упал.
- **Next.js ISR**: `revalidate: 60` на странице или fetch. Страница статическая, после 60 секунд первый визитёр получает старую, в фоне она пересобирается. Плюс on-demand `revalidateTag` / `revalidatePath` по событию.
- **React Query / SWR**: `staleTime` говорит, сколько данные считаются свежими; после этого при монтировании компонента или фокусе окна показываются кэшированные данные и уходит фоновый refetch. `gcTime` (раньше cacheTime) это сколько держать неиспользуемый кэш в памяти.

## Пример
```js
// React Query: список показывается из кэша мгновенно,
// в фоне обновляется, если прошло больше 30 секунд
const { data } = useQuery({
  queryKey: ["products"],
  queryFn: fetchProducts,
  staleTime: 30_000,
});

// после мутации помечаем ключ протухшим: следующий рендер
// покажет старый список и тут же подтянет новый
const mutation = useMutation({
  mutationFn: createProduct,
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ["products"] }),
});
```

То же самое на CDN одной строкой в ответе: `Cache-Control: s-maxage=60, stale-while-revalidate=600`. Edge отдаёт страницу за миллисекунды, origin видит один запрос в минуту, а не тысячу.

## Подводные камни
- SWR это осознанное согласие на stale: первый после истечения юзер видит старое. Для баланса счёта или корзины при оформлении это не подходит, там нужен запрос в источник или инвалидация по событию.
- `staleTime: 0` по умолчанию в React Query: при каждом монтировании refetch. Люди удивляются «почему столько запросов», а это дефолт, а не баг.
- stale-while-revalidate в HTTP работает, только если кэш его поддерживает: Chrome и Firefox да, CDN почти все, но не каждый прокси.
- Redis рядом с этим: ускоритель поверх БД, а не замена. Кэш, сессии, rate limiting, очереди туда можно; единственную копию важных данных нельзя, это память, она может пропасть. Ревалидация в фоне всегда идёт в источник правды.
- Красный флаг: кандидат знает `revalidate` в Next, но не может объяснить, что это тот же паттерн, что в React Query.

## Вопросы вдогонку
- **Чем staleTime отличается от gcTime в React Query?** staleTime это когда данные считаются протухшими и нужен фоновый refetch; gcTime это когда неиспользуемый кэш вообще выкидывают из памяти.
- **ISR vs SSR?** SSR рендерит на каждый запрос, ISR отдаёт статическую страницу и пересобирает её в фоне раз в N секунд или по событию.
- **Что такое stale-if-error?** Расширение той же идеи: если origin вернул 5xx или не ответил, отдать старую копию вместо ошибки.
- **Когда SWR не подходит?** Когда stale-данные стоят денег или доверия: платежи, остатки на складе при оформлении, права доступа.
