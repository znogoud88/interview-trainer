## Что это
**Коротко:** В HTTP два механизма кэша. Cache-Control говорит браузеру и CDN «сколько можно не спрашивать меня снова» (max-age=3600: час вообще не ходим на сервер). ETag это версия данных: клиент шлёт If-None-Match, сервер отвечает 304 Not Modified без тела, если ничего не поменялось. Первый экономит запрос целиком, второй только трафик.

Флоу с Cache-Control: запрос → ответ → сохранили в кэш. Следующий запрос: max-age не истёк, берём из кэша, сервер не трогаем. Заголовок ставит сервер (бэкенд или CDN), фронт влияет косвенно: хеш в имени файла, code splitting.

Директивы, которые надо знать:
- `max-age` сколько секунд хранить в браузере. `s-maxage` то же самое, но для CDN и прокси (shared cache), для них перебивает max-age.
- `no-cache` кэшировать МОЖНО, но перед каждым использованием спросить сервер (ревалидация через ETag). Это не «не кэшировать».
- `no-store` вообще не сохранять, ни в браузере, ни в CDN.
- `public` / `private`: public можно класть в общий кэш (CDN), private только в браузер конкретного юзера.
- `immutable`: файл никогда не поменяется, не ревалидируй даже по F5.

Флоу с ETag: сервер отдаёт `ETag: "abc123"` → клиент на следующий запрос шлёт `If-None-Match: "abc123"` → сервер либо 304 без тела, либо 200 с новым телом и новым ETag. Есть аналог по дате, `Last-Modified` / `If-Modified-Since`, но ETag точнее.

## Пример
```http
# статика с хешем в имени: год и не ревалидировать
GET /assets/app.abc123.js
Cache-Control: public, max-age=31536000, immutable

# HTML не кэшируем: он указывает на актуальный бандл
GET /index.html
Cache-Control: no-cache

# API: хранить можно, но каждый раз проверять
GET /api/products
Cache-Control: no-cache
ETag: "v42"
# следующий запрос: If-None-Match: "v42"  ->  304 Not Modified
```

Почему хеш в имени: если app.js закэширован на год, а мы задеплоили новую версию, у юзера старый JS, и UI ломается. С хешем новый билд даёт app.xyz789.js, браузер видит новое имя и качает заново. Инвалидация бесплатно, Vite, Webpack, Next делают это сами. Смотреть всё это в DevTools: Network → запрос → Headers, в колонке Size видно «(memory cache)» / «(disk cache)».

## Подводные камни
- Почему не всегда ETag: каждый раз всё равно идёт запрос на сервер. Даже если ответ 304 без тела, это round-trip и нагрузка. Для статики лучше max-age, чтобы запросов не было вообще.
- `no-cache` vs `no-store` классическая путаница. no-cache это «храни, но проверяй». Если нужно, чтобы не хранилось нигде (токены, персональные данные, платёжные страницы), то `no-store` плюс `private`.
- Персональный ответ с `public` или без `private` в CDN это чужая корзина из кэша. Один из самых частых инцидентов.
- Никогда не кэшировать: ответы с токенами и персональными данными, ответы на POST (обычно), ошибки осторожно (закэшированный 500 на 10 минут это самострел).
- Без заголовков браузер кэширует эвристически (по Last-Modified), поэтому «я ничего не ставил, почему оно закэшировалось» это нормальная ситуация.

## Вопросы вдогонку
- **Чем 304 отличается от ответа из кэша?** 304 это ответ сервера после запроса (сэкономили трафик, round-trip остался). Из кэша по max-age запроса не было вообще.
- **Что такое s-maxage и зачем он?** TTL для shared cache (CDN). Можно держать в CDN час, а браузеру отдать max-age=0, чтобы инвалидировать централизованно purge-ом на CDN.
- **Как фронт влияет на кэширование, если заголовки ставит сервер?** Хеш в имени файла, разбиение бандла (меняется один чанк, а не всё), договорённость с бэком о заголовках на HTML и API.
- **Как кэшировать HTML у SPA?** no-cache или не кэшировать: HTML это точка входа, он ссылается на свежие хешированные бандлы.
