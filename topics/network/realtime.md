## Что это
**Коротко:** Три способа получать обновления с сервера. Polling: клиент сам спрашивает раз в N секунд, просто, но лишние запросы и задержка. SSE: сервер льёт события в одну сторону по обычному HTTP, reconnect встроен, хватает для нотификаций, фидов, прогресса. WebSocket: двусторонний постоянный канал для чатов и совместного редактирования. Выбор по задаче: если нужен только push от сервера, SSE закрывает 80% «realtime» задач.

Сравнение:
- **Polling**: `setInterval(fetch)`. Нагрузка пропорциональна числу клиентов, а не событий; задержка до интервала. Long polling (держим запрос, пока нет события) лучше, но всё равно костыль.
- **SSE** (`EventSource`): один долгий GET, `Content-Type: text/event-stream`, сервер пишет `data: ...` строками. Плюсы: это HTTP, прокси и балансировщики дружат, автореконнект и `Last-Event-ID` встроены в браузер. Минусы: только сервер → клиент, и на HTTP/1.1 лимит 6 соединений на домен (на HTTP/2 не проблема).
- **WebSocket**: upgrade с HTTP на постоянный TCP-канал, сообщения в обе стороны с минимальным overhead. Плюс: латентность и двусторонность. Минус: состояние соединений на сервере, корпоративные прокси иногда режут, reconnect и heartbeat пишешь сам (или берёшь Socket.IO).

Почему не сокеты для всего: HTTP даёт кэш, статусы, retry, CDN, логирование, всю инфраструктуру. CRUD живёт на HTTP, сокет только там, где нужен push. Каждое открытое соединение это память и состояние на сервере.

## Пример
Полный флоу: событие в системе (заказ сменил статус) → сервис публикует в канал/room `order:123` → сервер пушит подписчикам → клиент вливает в состояние (`queryClient.setQueryData` или store). На фронте обёртка-сервис над сокетом, а не `socket.on` в каждом компоненте.

```js
// SSE: три строки, reconnect и Last-Event-ID бесплатно
const es = new EventSource("/api/orders/123/events");
es.onmessage = (e) => applyOrderUpdate(JSON.parse(e.data));
// при обрыве браузер сам переподключится и пришлёт Last-Event-ID
```

Reconnect у WebSocket: соединение упало, Socket.IO переподключается с backoff, но этого мало. Пока клиента не было, события прошли мимо. Нужна досинхронизация: клиент присылает последний полученный `eventId` или `version`, сервер отдаёт пропущенное; либо после reconnect запросить снапшот и дальше принимать дельты. Reconnect без досинка это дыры в данных, и это главный детектор глубины на собесе.

## Подводные камни
- Масштабирование: два инстанса сервера, юзер A подключён к первому, юзер B ко второму, сообщения друг друга не видят. Решение: адаптер pub/sub между инстансами (`@socket.io/redis-adapter`), каждый инстанс публикует в Redis, остальные доставляют своим клиентам. Плюс sticky sessions, чтобы handshake и fallback на long polling попадали на один инстанс.
- Rooms и auth: подписка на сущность (проект, чат, юзер), а не broadcast всем всё. Токен проверяем на handshake, права на `join` проверяем отдельно, иначе любой подпишется на чужой чат.
- Presence («кто онлайн»): heartbeat от клиента, ключ в Redis с TTL, истёк значит офлайн. Флаппинг (статус мигает при переподключении) лечится дебаунсом: офлайн показывать только через N секунд тишины.
- Утечки: подписки не снимаются при размонтировании, сервер держит мёртвые соединения без heartbeat.
- Красный флаг: «на всё WebSocket» или «SSE это устаревшее». Интервьюер ждёт трезвого выбора по задаче.

## Вопросы вдогонку
- **Почему SSE недооценён?** Работает по HTTP, reconnect из коробки, не нужна отдельная инфраструктура; для нотификаций, прогресса и фидов хватает.
- **Как не потерять данные при reconnect?** `Last-Event-ID` в SSE или свой lastEventId/version в сокете, сервер досылает пропущенное; либо снапшот плюс дельты.
- **Что ломается на двух инстансах?** Клиенты на разных инстансах не получают события друг друга; нужен общий pub/sub (Redis) между инстансами.
- **Как аутентифицировать WebSocket?** Токен на handshake (cookie, auth-поле Socket.IO или первое сообщение), проверка прав при подписке на room, отключение при протухании токена.
