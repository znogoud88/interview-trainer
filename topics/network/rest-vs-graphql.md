## Что это
**Коротко:** REST это ресурсы и HTTP-семантика: просто, кэшируется HTTP-кэшем, зрелые инструменты. GraphQL это один эндпоинт и запрос «дай мне ровно эти поля»: решает over/under-fetching и даёт один запрос на экран ценой сложности сервера. gRPC это бинарный protobuf поверх HTTP/2 для общения сервис-сервис, в браузере нативно не работает. Выбор по задаче и по количеству разных клиентов, а не по моде.

Что решает GraphQL:
- **Over-fetching**: REST отдаёт весь `/users/42`, а экрану нужны имя и аватар. В GraphQL просишь два поля.
- **Under-fetching**: экран собирается из 5 REST-вызовов (пост, автор, комментарии, лайки). В GraphQL один запрос с вложенностью.
- **Типизированная схема**: контракт самодокументируется, фронт генерит типы из схемы, есть introspection и playground.

Что это стоит:
- Сложность сервера: резолверы, и N+1 по умолчанию (резолвер на каждое поле каждого объекта), нужен DataLoader.
- HTTP-кэш мимо: всё идёт POST на `/graphql`, CDN и браузер не кэшируют. Кэш переезжает в клиент (Apollo, urql с нормализованным кэшем) и на сервер (persisted queries).
- Rate limiting и защита хитрее: один запрос может быть сколь угодно дорогим, нужны лимиты глубины и «стоимости» запроса.
- Статусы: почти всегда 200, ошибки внутри `errors[]`, мониторинг по статусам не работает.

gRPC: контракт в `.proto`, бинарная сериализация, стриминг в обе стороны, кодогенерация клиентов. Быстро и строго, поэтому живёт между микросервисами. Браузер не умеет говорить gRPC напрямую (нужен доступ к HTTP/2 фреймам и трейлерам), поэтому ставят прокси grpc-web или Connect. На фронте встречается редко.

## Пример
```graphql
# один запрос на экран карточки поста вместо 3-4 REST-вызовов
query PostCard($id: ID!) {
  post(id: $id) {
    title
    author { name avatarUrl }
    comments(first: 5) { edges { node { text author { name } } } }
  }
}
```
Тот же экран на REST: либо `GET /posts/7?include=author,comments` (эндпоинт под экран, BFF), либо несколько запросов параллельно. Для CRUD-админки с десятком экранов это нормально, и GraphQL там не окупится.

## Подводные камни
- Выбор: много разных клиентов и экранов (web, iOS, Android, партнёры) с разными потребностями в данных, тогда GraphQL окупается. Одна команда и CRUD, тогда REST хватит, а схема и резолверы это лишний слой.
- GraphQL не отменяет бэкенд-работу: под капотом те же БД-запросы, и если резолверы ходят в базу по полю, получаешь N+1 на ровном месте.
- «GraphQL быстрее» неправда по умолчанию. Меньше round-trip, но сервер делает больше работы, а HTTP-кэш потерян.
- HATEOAS (ссылки на следующие действия прямо в ответе, hypermedia) это часть «настоящего» REST по Fielding, но в реальных API почти не используется. Знать термин и трезво оценить, без карго-культа.
- Красный флаг: хайп в любую сторону. «REST устарел» или «GraphQL это мода» без trade-offs.

## Вопросы вдогонку
- **Как кэшировать GraphQL?** На клиенте нормализованный кэш (Apollo InMemoryCache по `__typename` + `id`), на сервере persisted queries через GET, чтобы CDN мог кэшировать.
- **Как GraphQL борется с N+1?** DataLoader: батчит запросы одного типа в рамках одного тика в `WHERE id IN (...)` и дедуплицирует по id.
- **Когда gRPC всё же на фронте?** Через grpc-web или Connect, когда бэк уже на gRPC и хочется один контракт; обычно проще поставить REST или GraphQL gateway.
- **Что такое BFF и как он связан с этим спором?** Backend for Frontend: слой под конкретный клиент, который собирает данные под экран. Часто это достаточная альтернатива GraphQL.
