## Что это
**Коротко:** REST это стиль API поверх HTTP: ресурсы в URL (`/users/42`), действие задаёт метод (GET читает, POST создаёт, PUT заменяет, PATCH меняет часть, DELETE удаляет), результат описывает статус-код. Слово-детектор понимания на собесе: идемпотентность. Повтор запроса даёт то же состояние сервера у GET, PUT, DELETE, но не у POST.

Методы и их семантика:
- **GET**: чтение, безопасный (ничего не меняет), поэтому его можно кэшировать и повторять сколько угодно.
- **POST**: создать или «сделать действие». Два POST = два заказа. Не идемпотентный.
- **PUT**: заменить ресурс целиком тем, что прислали. Повтор ничего не меняет, идемпотентный.
- **PATCH**: частичное обновление, прислал только изменённые поля. Формально не обязан быть идемпотентным (`{"op": "increment"}`), на практике обычно да.
- **DELETE**: удалить. Второй DELETE вернёт 404 или 204, но состояние сервера то же, значит идемпотентный.

Статусы, которые реально используют:
- `200 OK`, `201 Created` (после POST, часто с Location), `204 No Content` (DELETE, ответ без тела).
- `400 Bad Request` (кривой запрос, валидация), `422 Unprocessable Entity` (синтаксис ок, по смыслу нет, часто для валидации форм).
- `401 Unauthorized`: «кто ты?», сервер не знает, кто делает запрос (нет токена или он протух).
- `403 Forbidden`: «я знаю, кто ты, но тебе нельзя». Аутентифицирован, но прав нет.
- `404 Not Found`, `409 Conflict` (email занят, версия устарела), `429 Too Many Requests`, `500` (упал сервер), `502/503/504` (прокси: бэк недоступен, перегружен, таймаут).

## Пример
```http
GET    /posts/7/comments              -> 200 + список
POST   /posts/7/comments              -> 201 + созданный комментарий
PATCH  /comments/15  {"text": "..."}  -> 200 + обновлённый
DELETE /comments/15                   -> 204
DELETE /comments/15 (повтор)          -> 404, но ничего не сломалось: идемпотентно
```

Клиент на 401 идёт обновлять токен и повторяет запрос. На 403 обновлять токен бессмысленно: надо показать «нет доступа». Если фронт путает эти два, получается бесконечный цикл рефреша или зря разлогиненный юзер.

## Подводные камни
- «Всё 200 с `{ error: true }` внутри» это боль потребителя: fetch не отличит ошибку, кэш сохранит ошибку как успех, мониторинг ничего не увидит. Статус должен отражать результат.
- 401 называется Unauthorized, но означает unauthenticated. Это историческая путаница в самой спецификации, на собесе стоит её проговорить.
- Идемпотентность это про состояние сервера, а не про ответ. Второй DELETE вернёт другой статус, но всё равно идемпотентен.
- Практический смысл: ретраить по таймауту можно только идемпотентные запросы. POST без idempotency key ретраить нельзя, будет дубль.
- POST для чтения «потому что параметров много» ломает кэш и семантику. Если очень надо, то хотя бы осознанно.

## Вопросы вдогонку
- **PUT или PATCH для обновления профиля?** PATCH, если шлёшь только изменённые поля; PUT, если весь объект. Главное, чтобы бэк вёл себя так, как обещает метод.
- **Что вернуть на создание, 200 или 201?** 201 Created плюс тело или заголовок Location с адресом нового ресурса.
- **Почему GET нельзя использовать для действий?** Браузеры, прокси и краулеры могут повторить или предзагрузить GET. «Удаление по ссылке» однажды удалит всё.
- **400 или 422 на валидацию?** Оба встречаются; важнее, чтобы в команде было одно правило и единый формат тела ошибки.
