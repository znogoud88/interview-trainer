## Что это
**Коротко:** Хороший API с точки зрения фронта это консистентные ресурсы и статусы, один предсказуемый формат ошибок, пагинация и фильтры из коробки, данные под экран (а не 5 запросов на одну страницу) и OpenAPI-документация, из которой генерятся типы. Эти решения принимаются один раз в гайдлайнах: консистентность важнее идеальности каждого отдельного выбора.

Что обычно обсуждают:
- **Формат ошибок**: единый конверт с машиночитаемым `code`, человеческим `message` и `details` по полям. Правильный HTTP-статус плюс тело. Никаких stack trace наружу. Фронт мапит `details` на поля формы, это главное, что он от ошибок хочет.
- **Пагинация**: offset (`?page=3&limit=20`) простая и даёт «перейти на страницу 50», но «едет» при вставках (элемент появился в начале, и на следующей странице повтор) и медленная на глубоких страницах (БД пропускает 100k строк). Cursor (`?after=eyJpZCI6...`) стабильна для лент и бесконечного скролла, но нет прыжка на произвольную страницу. Выбор от UI: таблица со страницами или лента.
- **Версионирование**: `/v1/` в пути, заголовок (`Accept: application/vnd.api+json;version=2`), или эволюция без breaking changes (только добавляем поля). Нужно внешним потребителям и мобилкам, где старые версии живут месяцами. Внутреннему API одной команды часто хватает обратной совместимости.
- **Типы в синке с API**: генерация из OpenAPI (`openapi-typescript`, `orval`) или Zod-схемы на границе, которые дают и рантайм-валидацию, и типы. «Пишем интерфейсы руками и надеемся» это красный флаг.
- **Загрузка файлов**: мелкие через `multipart/form-data`. Большие через presigned URL: бэк выдаёт подписанную ссылку, клиент грузит напрямую в S3, сервер не пропускает файл через себя. Прогресс через `xhr.upload.onprogress`, resumable upload по чанкам для огромных. Валидация типа и размера на сервере обязательна, фронтовая только для UX.

## Пример
Мини-задача «спроектируй API комментариев»:
```http
GET    /posts/:id/comments?after=<cursor>&limit=20   -> { items: [...], nextCursor: "..." }
POST   /posts/:id/comments  { text }                  -> 201 + комментарий
PATCH  /comments/:id        { text }                  -> 200
DELETE /comments/:id                                  -> 204
```
Ошибка в одном формате везде:
```json
{ "code": "VALIDATION_ERROR", "message": "Проверьте поля",
  "details": [{ "field": "text", "code": "TOO_LONG", "message": "Максимум 2000 символов" }] }
```
С таким ответом `setError("text", ...)` в react-hook-form пишется один раз на весь проект.

## Подводные камни
- Offset-пагинация на ленте с частыми вставками даёт дубли и пропуски. Cursor для таблицы с номерами страниц не подходит. Выбирать от UI, а не «как привыкли».
- Cursor должен быть непрозрачным (base64 от id и sort key), иначе клиенты начнут его парсить, и его формат станет контрактом.
- `details` без `code` на поле: фронт вынужден матчить по тексту сообщения, а оно поменяется с локализацией.
- Версия в URL проще в отладке и кэшировании, версия в заголовке «чище», но её не видно в логах и ссылках. Чаще побеждает путь.
- Файлы через свой сервер: память и таймауты на больших файлах, двойной трафик. Presigned URL решает, но нужен CORS на бакете и ограничение по типу и размеру в самой подписи.
- На собесе ценят боль из опыта: «на 5 экранах разный формат ошибок» звучит сильнее, чем пересказ REST-учебника.

## Вопросы вдогонку
- **Что положить в API-гайдлайны новой команды?** Именование ресурсов, формат ошибок, пагинацию, версионирование, auth, решить один раз; OpenAPI как источник правды и генерация типов из него.
- **Как сделать удобный ответ списка?** `{ items, nextCursor }` или `{ items, total, page }`, но одинаково для всех списков, а не массив в одном месте и объект в другом.
- **Как не ломать клиентов при изменении API?** Только добавлять поля, не менять смысл существующих, deprecated помечать и убирать через новую версию.
- **Как показать прогресс загрузки?** `xhr.upload.onprogress` (у fetch прогресса отправки в браузерах толком нет), для chunked upload считать по отправленным кускам.
