## Что это
**Коротко:** Любой внешний API однажды затупит или упадёт, поэтому у каждого запроса должен быть таймаут, у повторов exponential backoff с jitter, а ретраить можно только идемпотентные запросы. Rate limiting это защита API от перегруза: сервер отвечает 429 Too Many Requests и `Retry-After`, а клиент обязан замедлиться, а не долбить дальше.

Инструменты против медленного или падающего API:
- **Таймаут** (обязательно): без него запрос висит вечно, а в Node ещё и держит соединение. На фронте `AbortSignal.timeout(5000)` в fetch.
- **Ретраи с backoff**: 1s, 2s, 4s плюс случайный jitter, чтобы тысяча клиентов не повторила запрос в одну секунду. Ограничить число попыток. Ретраить на сетевые ошибки, таймауты, 502/503/504 и 429, не на 400/401/403/404.
- **Не ретраить POST без идемпотентности**: таймаут не значит, что сервер не обработал. Повтор «создать платёж» = два платежа. Либо idempotency key, либо не ретраить.
- **Кэш ответов и graceful degradation**: показать последнее известное значение, спрятать блок с рекомендациями, а не ронять всю страницу.
- **Circuit breaker** (концептуально): если сервис отвечает ошибками подряд, перестаём его дёргать на N секунд и сразу отдаём fallback, потом пробуем одним запросом. Иначе таймауты копятся, и лежит уже наш сервис.
- **Фон или очередь** для необязательного: отправка email, аналитика, синхронизация с CRM не должны стоять на критическом пути.

На клиенте при 429: уважать `Retry-After`, backoff, очередь запросов (не больше N параллельно), дебаунс источника (поиск по вводу, autosave). Уважение к чужому API это признак зрелости.

## Пример
```js
async function fetchWithRetry(url, { retries = 3, signal } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      const res = await fetch(url, { signal: AbortSignal.any([signal, AbortSignal.timeout(5000)]) });
      if (res.ok) return res;
      const retryable = res.status === 429 || res.status >= 502;
      if (!retryable || attempt >= retries) throw new Error(`HTTP ${res.status}`);
      const retryAfter = Number(res.headers.get("Retry-After")) * 1000;
      await sleep(retryAfter || 2 ** attempt * 1000 + Math.random() * 300);
    } catch (e) {
      if (signal?.aborted) throw e;        // отменил юзер, не ретраим
      if (attempt >= retries) throw e;
    }
  }
}
// Только для GET/PUT/DELETE. POST сюда не заворачивать без Idempotency-Key.
```

## Подводные камни
- Дебаг «в Postman работает, в приложении нет»: системно сравнить два запроса. Заголовки (Authorization, Content-Type, Accept), cookie (браузер без `credentials: "include"` на другой origin их не отправит), CORS и preflight (OPTIONS не прошёл, в Network tab красный запрос перед основным), тело и encoding (JSON vs form-data). Postman живёт вне браузера, поэтому CORS там не существует вообще.
- Ретраи без backoff и jitter это retry storm: упавший сервис получает в 3 раза больше трафика и не встаёт.
- Ретраи на каждом слое (клиент 3, BFF 3, сервис 3) дают 27 запросов. Договориться, кто ретраит.
- 429 обрабатывают как обычную ошибку и показывают юзеру «что-то пошло не так», хотя надо было подождать секунду и повторить тихо.
- Таймаут должен быть короче, чем у того, кто тебя ждёт, иначе вышестоящий отвалится раньше, а ты продолжишь работать впустую.

## Вопросы вдогонку
- **Чем 429 отличается от 503?** 429 это «ты слишком часто», лимит на клиента; 503 это «я перегружен», проблема на сервере. Оба могут нести `Retry-After`.
- **Как сделать POST безопасным для ретраев?** Клиент генерирует `Idempotency-Key` (uuid), сервер хранит результат по ключу и на повтор отдаёт тот же ответ.
- **Что такое jitter и зачем?** Случайная добавка к задержке, чтобы клиенты не синхронизировались и не били сервер волнами.
- **Где живёт rate limiting?** На gateway или в middleware: token bucket или sliding window, счётчик в Redis по ключу user/ip/api-key.
