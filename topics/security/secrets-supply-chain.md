## Что это
**Коротко:** Секреты (API-ключи, токены, пароли к базе) живут в env вне репозитория, в секрет-менеджере или в секретах CI, и никогда в git. Зависимости это вторая дверь: аудит в CI, lockfile, автообновления через dependabot или renovate, и не ставить пакеты бездумно, потому что supply chain атаки идут через npm. Пароли юзеров хранить только через bcrypt или argon2, а лучше вообще не строить auth самому.

Секреты:
- `.env` в `.gitignore`, в репо только `.env.example` с пустыми значениями.
- В проде секрет-менеджер (AWS Secrets Manager, Vault, Doppler) или переменные окружения платформы. В CI встроенные secrets, в логи они маскируются.
- Фронтовый бандл это публичное место. Всё, что с префиксом `NEXT_PUBLIC_` или `VITE_`, уезжает в браузер. Секрет туда класть нельзя, там место только для публичных ключей (Google Maps с ограничением по домену, publishable key Stripe).

Supply chain:
- `npm audit` / `pnpm audit` в CI, но не как единственная защита: он знает только опубликованные CVE.
- Lockfile обязателен и ставится через `npm ci`, чтобы на проде был ровно тот набор, что тестировали.
- Тайпосквоттинг: `lodahs`, `cross-env.js`. Скомпрометированные мейнтейнеры: event-stream, ua-parser-js, colors. Код выполняется уже на `npm install` через postinstall.
- Slopsquatting: AI уверенно выдумывает пакеты, которых нет. Злоумышленник регистрирует это имя, следующий, кто скопирует ответ модели, ставит малварь. Проверять, что пакет существует и кто его автор.

Пароли, если всё-таки строишь auth сам: bcrypt или argon2id, они медленные специально и солят сами. Никогда plain, md5, sha1, sha256 без соли: такие хэши перебираются по радужным таблицам за минуты. Rate limiting на `/login` от перебора.

## Пример
```js
// ❌ секрет в бандле: VITE_ префикс = уедет в браузер, любой откроет Sources
const client = new OpenAI({ apiKey: import.meta.env.VITE_OPENAI_KEY });

// ✅ ключ только на сервере, фронт ходит в свой бэк
// server.js
const client = new OpenAI({ apiKey: process.env.OPENAI_KEY });
app.post("/api/ask", requireAuth, rateLimit, (req, res) => client.chat(...));
```

Классика из жизни: ключ закоммитили, через час удалили коммитом «remove key». Git хранит историю, ключ виден в `git log -p` и в любом форке. Боты сканируют GitHub на паттерны ключей за минуты.

## Подводные камни
- Утёк = ротация немедленно. Удалить из кода недостаточно, переписать историю тоже: ключ уже скопирован. Сначала отозвать, потом чистить.
- Логирование токенов: `console.log(req.headers)` или дамп axios-конфига с `Authorization` уезжает в Sentry или в логи, где его читают все, у кого есть доступ.
- Мажорный апдейт по dependabot мержить глазами: lockfile меняется на сотни строк, и постinstall-скрипт нового пакета это и есть вектор. `--ignore-scripts` для CI, где можно.
- Автообновления сразу после релиза это риск: взломанные версии живут часы, пока их не снимут. Cooldown на новые версии в renovate или `minimumReleaseAge` в pnpm.
- Лучший ответ про auth на собесе: «сам не строю, Auth0, Cognito, Keycloak, Supabase Auth», но механику bcrypt и rate limiting знать надо. Красный флаг: «sha256 с солью, норм».

## Вопросы вдогонку
- **Чем bcrypt отличается от sha256?** Медленный по дизайну с настраиваемым cost, соль встроена. sha256 считается миллиардами в секунду на GPU.
- **Что делать, если ключ попал в git?** Отозвать и выпустить новый, проверить логи на использование, потом уже чистить историю через `git filter-repo`, если репо приватный и это имеет смысл.
- **Зачем lockfile, если версии зафиксированы в package.json?** `^1.2.3` это диапазон, транзитивные зависимости вообще не зафиксированы. Lockfile даёт воспроизводимую установку.
- **Как проверить пакет перед установкой?** Автор, дата, количество загрузок, репозиторий, что он реально существует на npm, нет ли postinstall. `npm view <pkg>` перед `npm i`.
