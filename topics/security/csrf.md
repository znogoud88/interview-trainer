## Что это
**Коротко:** CSRF (Cross-Site Request Forgery) это когда чужой сайт заставляет твой браузер сделать запрос на твой сервер от твоего имени. Работает, потому что cookie добавляются к запросу автоматически, и сервер думает, что «это ты». Защита: SameSite cookies, CSRF-токен, который приходит не в cookie, и проверка `Origin` на бэке.

Почему работает: ты залогинен в банке, cookie сессии живёт в браузере. Открываешь сайт злоумышленника, там `<img src="https://bank.com/transfer?...">` или скрытая форма с автосабмитом. Браузер делает запрос на bank.com и прикладывает cookie bank.com, как всегда. Сервер видит валидную сессию и выполняет перевод.

Три защиты:
- **SameSite cookie**. `Strict`: cookie вообще не уходит с чужого сайта. `Lax`: уходит только при top-level переходе по ссылке (GET), не уходит с POST, img, iframe, fetch. `None`: уходит всегда, обязателен `Secure`. Chrome с 2020 по умолчанию ставит `Lax`.
- **CSRF token**. Сервер выдаёт уникальный токен, клиент обязан вернуть его в body или в заголовке. Не в cookie: cookie улетит сама, в этом вся суть атаки. Чужой сайт токен не знает, потому что не может прочитать ответ твоего сервера (CORS).
- **Проверка Origin / Referer**. Браузер сам добавляет `Origin: https://evil.com` к cross-site POST, бэк сверяет с whitelist и отклоняет. Фронт тут ничего не настраивает, это работа бэка.

## Пример
```html
<!-- ❌ сайт злоумышленника, юзер залогинен в bank.com -->
<img src="https://bank.com/transfer?amount=1000&to=hacker" />
<!-- браузер отправит cookie, деньги ушли -->
```

```http
✅ тот же перевод с CSRF-токеном
POST /transfer
Cookie: session=xyz
X-CSRF-Token: abc123
Body: { "amount": 1000, "to": "..." }
```

Сервер сравнивает `abc123` с токеном, который привязан к сессии `xyz`. Чужой сайт может заставить браузер отправить cookie, но не может подставить токен, которого не видел.

## Подводные камни
- Bearer токен в заголовке `Authorization` CSRF не грозит: заголовок сам не полетит, его добавляет наш JS. Чужой сайт не может поставить кастомный заголовок без CORS preflight, который наш сервер не разрешит. Поэтому CSRF это проблема именно cookie-based auth.
- CORS от CSRF не защищает. CORS блокирует чтение ответа, а простой POST формы улетит и выполнится. Деньги уйдут, злоумышленник просто не увидит ответ.
- GET, который меняет состояние, это дыра даже при `SameSite=Lax`: переход по ссылке cookie пронесёт. Мутации только через POST/PUT/DELETE.
- `Lax` не спасает, если cookie нужна в cross-site контексте (виджет в iframe на партнёрском сайте). Тогда `None; Secure` и обязательно токен.
- Красный флаг: «у нас JWT, CSRF не про нас», когда этот JWT лежит в cookie. Дело не в формате токена, а в том, как он доставляется.

## Вопросы вдогонку
- **Чем CSRF отличается от XSS?** XSS это чужой код на твоей странице. CSRF это чужая страница делает запрос на твой сервер с твоими cookie. XSS, кстати, обходит любую CSRF-защиту, потому что читает токен со страницы.
- **Что такое double submit cookie?** Токен кладут в cookie и его же требуют в заголовке. Чужой сайт cookie не прочитает, заголовок не подставит. Вариант, когда у сервера нет состояния.
- **Нужна ли CSRF-защита, если refresh token в HttpOnly cookie?** Да, хотя бы `SameSite=Strict` или `Lax` плюс проверка Origin на `/refresh`. Иначе чужой сайт выпустит новый access token за тебя.
- **Как фронт получает CSRF-токен?** Из meta-тега в HTML, из ответа `/csrf`, или читает из не-HttpOnly cookie при double submit, и кладёт в заголовок каждого мутирующего запроса.
