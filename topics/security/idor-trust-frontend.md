## Что это
**Коротко:** IDOR (Insecure Direct Object Reference) это когда `/orders/123` открывает твой заказ, меняешь на `124` и видишь чужой. Сервер проверил, что ты залогинен, но не проверил, что ресурс твой. Это частный случай общего правила: всё, что приходит с клиента, подделывается, поэтому валидация, авторизация и расчёт денег живут на сервере, на каждом эндпоинте.

Почему фронту нельзя доверять:
- Юзер контролирует браузер целиком: DevTools, Network tab, Postman, curl. Любой запрос можно собрать руками с любым телом.
- Цена товара в теле `POST /checkout` это подсказка, а не истина. Сервер берёт id товара и считает сумму сам.
- Валидация формы на фронте это UX (подсветить поле до отправки). Та же валидация на сервере это защита.
- Роль и права в state нужны, чтобы спрятать кнопку. Проверка `user.id === order.userId` на сервере нужна, чтобы кнопка не сработала у чужого.

Чем IDOR отличается от «нет авторизации»: аутентификация есть, 401 ты не получишь. Дыра именно в отсутствии ownership-проверки. Поэтому его легко пропустить: с виду всё защищено, middleware `requireAuth` стоит.

Почему AI-генерированный код часто с IDOR: попросишь «сделай CRUD для orders», получишь `findById(req.params.id)` без `userId`. Модель пишет по самому частому шаблону, а в туториалах ownership-проверки нет. Свежая связка тем на собесах: кандидат ревьюит сгенерированный код, должен это заметить.

## Пример
```js
// ❌ IDOR: проверили, что залогинен, не проверили, чей заказ
app.get("/orders/:id", requireAuth, async (req, res) => {
  const order = await db.order.findUnique({ where: { id: req.params.id } });
  res.json(order);
});

// ✅ ownership в самом запросе, чужой заказ просто не найдётся
app.get("/orders/:id", requireAuth, async (req, res) => {
  const order = await db.order.findFirst({
    where: { id: req.params.id, userId: req.user.id },
  });
  if (!order) return res.status(404).end();
  res.json(order);
});
```

То же самое для `PATCH`, `DELETE`, для вложенных ресурсов (`/orders/123/items/5`: проверяем и заказ, и что item принадлежит этому заказу), для файлов по URL.

## Подводные камни
- UUID вместо числовых id не лечит IDOR, только мешает перебору. Если ссылка утекла, ресурс открыт. Это obscurity, а не authorization.
- Проверка должна быть на каждом эндпоинте, не только на `GET`. Классика: список защищён, а `DELETE /orders/:id` нет.
- Mass assignment из той же семьи: `PATCH /me` с `{ "isAdmin": true }` в теле, бэк делает `update(req.body)`. Явный whitelist полей.
- 404 vs 403 для чужого ресурса: 404 не раскрывает существование, 403 честнее. Главное, чтобы ответ был одинаковым для «нет» и «не твой», иначе можно перебирать.
- Фронт тоже вносит вклад: не хардкодить id в URL без необходимости, не класть в state данные, которых юзер не должен видеть (например, полный объект с чужими полями, который фронт «фильтрует»).
- Красный флаг: «у нас кнопка скрыта» или «id это uuid, не угадаешь».

## Вопросы вдогонку
- **Как найти IDOR в своём приложении?** Залогиниться двумя юзерами, взять id у первого, дёрнуть все эндпоинты от второго. Автоматизируется в интеграционных тестах.
- **Что должно быть на сервере обязательно?** Валидация входа, авторизация каждого запроса (аутентификация + ownership + права), расчёт денег и скидок, лимиты.
- **Где граница между «фронт проверяет для UX» и дублированием логики?** Фронт проверяет то, что улучшает отклик: формат email, обязательные поля, видимость кнопок. Бизнес-правила живут на сервере, фронт их только отражает.
- **А если это admin-эндпоинт, там нет владельца?** Тогда проверяется роль или permission, но тоже на сервере и тоже на каждом эндпоинте, не на уровне «страница /admin скрыта».
