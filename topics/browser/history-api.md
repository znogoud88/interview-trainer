## Что это
**Коротко:** History API это набор методов, которые позволяют менять URL и управлять историей навигации без перезагрузки страницы. На этом держится роутинг в SPA: раньше `/page1` и `/page2` это два запроса к серверу и два reload, сейчас URL меняется, контент перерисовывается, страница остаётся. По сути это контроль над URL как над state.

Методы и событие:
- `history.pushState(state, "", "/products")`: добавляет новую запись в историю. URL меняется, страница не перезагружается, «назад» вернёт на предыдущий URL.
- `history.replaceState(state, "", "/dashboard")`: заменяет текущую запись, новой не добавляет. Зачем: redirect после логина. Если сделать pushState, «назад» вернёт на страницу логина, которая уже не нужна. Ещё для очистки query params, исправления URL, прочих редиректов.
- `popstate`: событие на `window`, срабатывает при «назад» и «вперёд» (и при `history.back()/forward()/go()`). Несмотря на название, это не pop как у массива: и вперёд тоже. На свой `pushState`/`replaceState` событие не срабатывает, роутер сам знает, что сделал.
- `history.back()`, `forward()`, `go(-2)`: программная навигация по истории.
- `state` в первом аргументе: объект, который сохраняется в записи истории и приходит в `event.state` при popstate. Туда кладут положение скролла, состояние формы, id.

Зачем: SPA-навигация без reload, человеческие URL (`/about` вместо `/#about`), работающие кнопки браузера, восстановление состояния при возврате. API работает в пределах одной вкладки.

## Пример
```js
// мини-роутер
function navigate(path) {
  history.pushState({ scrollY: window.scrollY }, "", path);
  render(path);                       // popstate тут НЕ сработает, рендерим сами
}

window.addEventListener("popstate", (e) => {
  render(location.pathname);          // юзер нажал назад/вперёд
  if (e.state?.scrollY != null) window.scrollTo(0, e.state.scrollY);
});

// ❌ после логина: «назад» вернёт на /login
history.pushState({}, "", "/dashboard");

// ✅ запись /login заменяется, в истории её нет
history.replaceState({}, "", "/dashboard");
```

В React Router это `navigate("/dashboard", { replace: true })`, в Next.js `router.replace`. Под капотом тот же `replaceState`.

## Подводные камни
- Сервер должен отдавать `index.html` на любой путь (fallback), иначе `/products/42` при reload или прямом заходе даст 404. Классическая ошибка деплоя SPA на nginx/S3.
- Менять можно только URL в пределах своего origin, `pushState` на другой домен кинет `SecurityError`.
- `pushState` на каждый ввод в поиск засоряет историю: «назад» перебирает каждую букву. Для фильтров и поиска `replaceState`.
- Если забыть обработать `popstate`, URL меняется, а контент нет. Если рендерить и в `navigate`, и из `popstate` без разбора, легко получить двойной рендер.
- Скролл не восстанавливается сам, как на обычных страницах. В SPA это руками: `history.scrollRestoration = "manual"` плюс своя логика на `state`.
- Старый вариант через `#hash` и `hashchange` до сих пор встречается в legacy: не требует настройки сервера, но URL некрасивые и hash не уходит на сервер.

## Вопросы вдогонку
- **Чем pushState отличается от `location.href = ...`?** `location.href` это полноценная навигация с запросом к серверу и перезагрузкой, `pushState` только меняет URL и историю.
- **Когда replaceState вместо pushState?** Редирект после логина, нормализация URL, обновление фильтров и поиска, любой случай, когда предыдущее состояние не должно быть доступно по «назад».
- **Что такое Navigation API?** Новый API (есть в Chrome, не везде), который заменяет связку pushState + popstate одним событием `navigate` с перехватом. Роутеры пока на History API.
- **Как перехватить уход с несохранённой формой?** Внутри SPA через роутер (блокировка перед навигацией), для закрытия вкладки `beforeunload`.
