## Что это
**Коротко:** JS в браузере однопоточный: один call stack, и пока он не пуст, ничего другого не происходит. Event loop это цикл, который берёт следующую задачу из очереди, когда stack опустел. Задачи двух видов: макрозадачи (task: `setTimeout`, события, колбэки I/O) и микрозадачи (microtask: `Promise.then`, `queueMicrotask`, `MutationObserver`). Микрозадачи выполняются все сразу после текущей задачи, до следующей макрозадачи и до рендера.

Один оборот цикла:
1. Взять одну задачу из task queue (скрипт целиком, callback setTimeout, обработчик клика), выполнить до конца. Прервать её нельзя.
2. Опустошить очередь микрозадач целиком. Если микрозадача добавила новую микрозадачу, она тоже выполнится сейчас.
3. Если пора рисовать кадр (примерно раз в 16.6 мс при 60Hz): выполнить колбэки `requestAnimationFrame`, потом style, layout, paint. Рендер это не задача, а отдельный шаг, браузер вставляет его между задачами, когда считает нужным.
4. Повторить.

Следствия: `Promise.then` всегда раньше `setTimeout(fn, 0)`, потому что микрозадачи идут до следующей задачи. `setTimeout(fn, 0)` это «после текущей задачи и всех микрозадач, не раньше», а не «сейчас». Долгая синхронная задача или бесконечная цепочка микрозадач не даёт браузеру добраться до шага 3, UI замирает.

Web API (таймеры, fetch, события) работают вне JS-потока: браузер сам ждёт, а когда готово, кладёт callback в очередь. Поэтому `setTimeout(fn, 1000)` это «не раньше чем через секунду», точное время зависит от того, когда stack освободится.

## Пример
```js
console.log("1 sync");

setTimeout(() => console.log("5 timeout"), 0);

Promise.resolve().then(() => {
  console.log("3 micro");
  queueMicrotask(() => console.log("4 micro from micro"));
});

console.log("2 sync");
// Вывод: 1 sync, 2 sync, 3 micro, 4 micro from micro, 5 timeout
```

Почему так: скрипт целиком это одна задача, оба `console.log` синхронные. `setTimeout` отдал callback браузеру, тот положит его в task queue. `.then` положил микрозадачу. Скрипт закончился, stack пуст, опустошаем микрозадачи: «3», она добавила «4», она тоже сейчас. Только потом следующая задача, «5». Рендер, если он нужен, случится между «4» и «5», но не внутри микрозадач.

`async/await` это тот же механизм: `await` разбивает функцию, продолжение после `await` это микрозадача.

## Подводные камни
- Long task: задача дольше 50 мс на main thread блокирует клики, скролл, анимации. INP страдает именно от них. Лечение: дробить на чанки через `setTimeout`/`scheduler.yield()`, тяжёлое в Web Worker.
- Микрозадачи не спасают от блокировки: 10 000 `.then` подряд выполнятся до рендера так же, как один синхронный цикл. Чтобы дать браузеру отрисовать, нужна макрозадача.
- `setTimeout(fn, 0)` это минимум 4 мс при вложенности от 5 уровней, в фоновой вкладке таймеры троттлятся до секунды и больше. На него нельзя опираться как на точные часы.
- Анимация на `setTimeout` дёргается, потому что не синхронизирована с кадрами. Для неё `requestAnimationFrame`.
- Node.js: тот же принцип, но очереди устроены иначе (фазы libuv, `process.nextTick` раньше промисов, `setImmediate`). На фронтовом собесе достаточно сказать, что отличается.
- Интервьюер проверяет, можешь ли ты объяснить порядок вывода, а не выучил ли слово. Красный флаг: «setTimeout 0 выполняется сразу» или «JS многопоточный, потому что есть fetch».

## Вопросы вдогонку
- **Почему `await` в цикле не вешает страницу?** Каждый `await` отдаёт управление, продолжение приходит микрозадачей. Но если промисы уже resolved, микрозадачи идут подряд без рендера, страница всё равно замрёт.
- **Где выполняется callback `fetch`?** Сам запрос делает браузер вне JS. Когда ответ пришёл, промис резолвится, обработчик `.then` попадает в очередь микрозадач.
- **Что такое `requestIdleCallback`?** Колбэк, который браузер вызовет, когда в кадре осталось свободное время. Для необязательной работы: аналитика, prefetch.
- **Как сделать, чтобы тяжёлый цикл не вешал UI?** Разбить на порции и между ними `await new Promise(r => setTimeout(r))` или `scheduler.yield()`, либо вынести в Web Worker.
