## Что это
**Коротко:** Набор «прод-маркеров», по которым видно, работал ли человек с живой базой. Соединение с базой дорогое, поэтому его переиспользуют через пул. View это сохранённый запрос, materialized view это сохранённый результат. Soft delete это пометка `deleted_at` вместо настоящего DELETE. Бэкап, который ни разу не восстанавливали, это не бэкап.

**Connection pooling.** Открыть соединение с Postgres это TCP handshake, TLS, аутентификация и отдельный процесс на стороне базы: десятки миллисекунд и память. Пул держит N открытых соединений и выдаёт их запросам по очереди: взял, выполнил, вернул. У базы есть лимит `max_connections` (обычно 100-200), выше него она просто отказывает. Боль serverless: тысяча параллельных лямбд, каждая со своим пулом, это тысяча соединений, и база падает. Лечится внешним пулером между приложением и базой: pgBouncer, RDS Proxy, Supavisor.

**View и materialized view.** View это именованный SELECT: `CREATE VIEW active_customers AS SELECT ...`. При обращении база каждый раз выполняет запрос заново, данных внутри нет, это просто удобное имя для сложного JOIN. Materialized view хранит результат на диске: тяжёлая агрегация для отчёта считается раз в час (`REFRESH MATERIALIZED VIEW`), а дашборд читает готовую таблицу за миллисекунды. По сути это кэш на уровне базы со всеми его вопросами: когда обновлять и насколько устаревшие данные допустимы.

**Soft delete vs hard delete.** Hard: `DELETE FROM users`, строка исчезла, вместе с ней по CASCADE может уйти всё связанное, восстановить только из бэкапа. Soft: `UPDATE users SET deleted_at = now()`, строка на месте, можно восстановить, есть аудит. Но теперь каждый запрос должен помнить `WHERE deleted_at IS NULL`, а unique constraint на email ломается: удалённый юзер занимает email. Финансовое и аудируемое почти всегда soft или перенос в архивную таблицу.

**Бэкапы.** Регулярный полный дамп плюс point-in-time recovery: база непрерывно пишет WAL, и можно восстановиться на любую секунду, например за минуту до того, как кто-то выполнил `DELETE` без `WHERE`. Главное правило: непроверенный бэкап равен отсутствию бэкапа. Он может быть пустым, битым, от не той базы или восстанавливаться 14 часов, и узнаешь это во время пожара. Восстановление тестируют заранее и регулярно.

**Логика в базе или в приложении.** Современный дефолт: бизнес-логика в приложении, где есть тесты, версионирование и код-ревью. Базе остаётся целостность: constraints, foreign keys, unique, NOT NULL. Триггеры и stored procedures это «магия», которую через год никто не помнит и которая не видна в коде.

## Пример
```js
// ❌ serverless без пулера: каждая лямбда открывает своё соединение,
// 1000 параллельных вызовов = 1000 соединений, Postgres с max_connections=100
// отвечает "FATAL: too many connections"

// ✅ приложение ходит через pgBouncer в transaction mode:
// 1000 лямбд делят 20 реальных соединений с базой
```
```sql
-- soft delete: частичный unique index, чтобы удалённый юзер не занимал email
CREATE UNIQUE INDEX users_email_active ON users (email) WHERE deleted_at IS NULL;
```

## Подводные камни
- Пул на стороне приложения не отменяет внешний пулер: 10 инстансов API с пулом по 20 это уже 200 соединений. Считать суммарно.
- Утечка соединений: взял из пула, кинул исключение, не вернул. Пул пустеет, запросы висят в ожидании, выглядит как «база тормозит», а база простаивает.
- Materialized view отстаёт от данных: юзер создал заказ, в отчёте его нет до следующего REFRESH. Об этом надо сказать в UI или обновлять чаще.
- Soft delete и GDPR: «удалить мои данные» означает hard delete или анонимизацию, пометка не подходит.
- Интервьюер хочет услышать «восстанавливал реально». Красный флаг: «бэкапы делает хостинг» без знания, как и за сколько их поднять.

## Вопросы вдогонку
- **Чем transaction mode в pgBouncer отличается от session mode?** В transaction mode соединение отдаётся клиенту только на время транзакции, их нужно меньше, но session-level вещи (`SET`, advisory locks, часть prepared statements) не работают.
- **Когда materialized view, а когда Redis?** Materialized view, когда результат это SQL-агрегация и допустимо отставание. Redis, когда нужен кэш произвольных объектов с TTL.
- **Как сделать unique email при soft delete?** Partial unique index с `WHERE deleted_at IS NULL`.
- **Что такое RPO и RTO?** RPO: сколько данных можно потерять (интервал бэкапов). RTO: за сколько должны подняться. Вместе определяют, какой бэкап нужен.
