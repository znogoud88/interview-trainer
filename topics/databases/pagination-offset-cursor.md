## Что это
**Коротко:** Offset-пагинация это `LIMIT 20 OFFSET 100000`: база читает 100 020 строк и выбрасывает первые 100 000, поэтому глубокие страницы медленные. Cursor-пагинация это `WHERE id > last_id LIMIT 20`: база по индексу прыгает сразу к нужному месту, любая страница стоит одинаково. Offset для таблиц с номерами страниц, cursor для лент и бесконечного скролла.

Почему offset тормозит: OFFSET не умеет «перемотать» индекс. База должна пройти все пропускаемые строки (прочитать, отсортировать, отбросить), работа растёт линейно с номером страницы. Первая страница быстрая, сотая в 100 раз дороже. Плюс `COUNT(*)` для «всего страниц: 5000» на большой таблице это ещё один полный проход.

Почему offset «едет»: между страницей 1 и 2 кто-то добавил запись в начало ленты. Все строки сдвинулись на одну, страница 2 начинается с того элемента, которым закончилась первая. Удалили запись, элемент проскочил. В ленте с активными вставками это видно как дубли и пропуски.

Cursor: клиент получает вместе со страницей курсор, обычно id или `created_at + id` последнего элемента, часто закодированный в base64, чтобы не было соблазна его парсить. Следующий запрос: `WHERE (created_at, id) < (cursor_created_at, cursor_id) ORDER BY created_at DESC, id DESC LIMIT 20`. Работает по индексу, вставки сверху не сдвигают уже прочитанное.

Что cursor не умеет: «перейти на страницу 50», «всего 1234 записи», сортировку по произвольной колонке без индекса. Поэтому выбор от UI: админка с таблицей и номерами страниц это offset (и там обычно данных немного), лента, чат, бесконечный скролл это cursor.

## Пример
```sql
-- ❌ offset: страница 5000 читает и выбрасывает 100k строк
SELECT * FROM posts ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 100000;

-- ✅ cursor: прыжок по индексу (created_at, id), любая страница одинаково быстрая
SELECT * FROM posts
WHERE (created_at, id) < ('2026-11-10 12:00:00', 48213)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

В API это `GET /posts?cursor=eyJjcmVhdGVkQXQiOi4uLn0&limit=20` и ответ `{ items: [...], nextCursor: "..." | null }`. На фронте с React Query это `useInfiniteQuery` с `getNextPageParam: (last) => last.nextCursor`.

## Подводные камни
- Курсор по одному `created_at` ломается на одинаковых значениях: два поста в одну миллисекунду, один потеряется. Поэтому в курсор всегда добавляют уникальный tie-breaker (id).
- Курсор привязан к сортировке. Юзер поменял сортировку с «новые» на «популярные», старый курсор бессмысленный, начинаем заново.
- Offset не «плохой», он просто не масштабируется. На таблице в 10 тысяч строк с номерами страниц он нормальный и проще.
- Что интервьюер хочет услышать: почему именно offset медленный (строки читаются и выбрасываются) и что выбор от UI. Красный флаг: «cursor всегда лучше» без понимания, что теряем номера страниц и count.

## Вопросы вдогонку
- **Как показать «страница 3 из 50» с cursor?** Никак честно. Либо отдельный приблизительный count, либо «ещё есть / больше нет», либо признать, что нужен offset.
- **Что такое keyset pagination?** То же, что cursor: WHERE по значениям последней строки вместо OFFSET.
- **Зачем курсор кодируют в base64?** Чтобы клиент относился к нему как к непрозрачному токену, а сервер мог менять формат, не ломая клиентов.
- **Можно ли cursor с сортировкой по нескольким колонкам?** Да, row comparison `(a, b, id) < (...)`, при условии, что на эти колонки есть составной индекс в том же порядке.
