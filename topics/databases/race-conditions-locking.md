## Что это
**Коротко:** Race condition это когда два параллельных запроса читают одно состояние и оба на его основе принимают решение. Остаток 1, оба `SELECT` вернули 1, оба проверили `stock > 0`, оба сделали `UPDATE stock = 0` и создали заказ. Продали два товара из одного. Транзакция сама по себе не спасает: чтение в обеих транзакциях честно увидело 1.

Три способа починить, от простого к сложному:
- **Атомарный UPDATE с условием.** Не читать и проверять в коде, а переложить проверку на базу: `UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0`. База меняет строку под блокировкой, второй запрос дождётся первого, увидит уже 0, условие не сработает, затронуто 0 строк. Смотрим на количество обновлённых строк: 0 значит «нет в наличии». Самый дешёвый и правильный вариант для счётчиков.
- **Pessimistic lock.** `SELECT ... FOR UPDATE` внутри транзакции: строка заблокирована до COMMIT, второй читатель ждёт. Нужен, когда логика между чтением и записью сложнее, чем «вычесть единицу», и должна жить в коде. Минус: ждущие соединения, риск deadlock, не работает через HTTP (нельзя держать блокировку, пока юзер думает).
- **Optimistic locking.** Колонка `version`. Читаем строку с version = 7, считаем в коде, пишем `UPDATE ... SET ..., version = 8 WHERE id = ? AND version = 7`. Если кто-то успел раньше, version уже 8, затронуто 0 строк, получаем конфликт и либо ретраим, либо показываем юзеру. Никто никого не ждёт, подходит для редких конфликтов и для сценариев через HTTP (version едет на фронт и обратно).

Та же проблема в realtime: два инженера редактируют одну запись. Без защиты получается last-write-wins: кто позже нажал «сохранить», тот перетёр чужие изменения, и никто не заметил. Варианты те же: блокировка («документ редактирует Вася»), версия с ответом 409 и merge на клиенте, или для настоящего совместного редактирования OT/CRDT, где изменения сливаются автоматически по частям, а не документом целиком.

## Пример
```js
// ❌ check-then-act: между SELECT и UPDATE влезает второй запрос
const p = await db.product.findUnique({ where: { id } });
if (p.stock > 0) {
  await db.product.update({ where: { id }, data: { stock: p.stock - 1 } });
  await db.order.create({ data: orderData });
}

// ✅ проверка и запись в одном атомарном UPDATE
const { count } = await db.product.updateMany({
  where: { id, stock: { gt: 0 } },
  data: { stock: { decrement: 1 } },
});
if (count === 0) throw new OutOfStock();
await db.order.create({ data: orderData }); // в одной транзакции с UPDATE
```

На фронте optimistic locking выглядит так: форма пришла с `version: 7`, PUT отправляет его обратно, сервер отвечает 409 Conflict, UI говорит «запись изменили, обновите» или показывает diff.

## Подводные камни
- «Обернул в транзакцию, значит безопасно» это самый частый ложный ответ. На Read Committed две транзакции спокойно читают одно и то же значение. Нужен либо UPDATE с условием, либо FOR UPDATE, либо Serializable с ретраями.
- Проверка в коде приложения (`if (stock > 0)`) не атомарна в принципе, сколько бы инстансов сервера ни было. Единственная точка, где все запросы встречаются, это база.
- Unique constraint тоже защита от гонок: два параллельных «создать аккаунт с email X» не пройдут оба, второй получит ошибку от базы. Проверка «есть ли такой email» перед INSERT не спасает.
- Что хочет интервьюер: кандидат видит, что проблема в «прочитал, потом записал», и знает хотя бы атомарный UPDATE. Красный флаг: «это очень редко, не страшно» или «сделаю мьютекс в Node».

## Вопросы вдогонку
- **Optimistic или pessimistic?** Optimistic, когда конфликты редкие и ждать нельзя (HTTP, формы). Pessimistic, когда конфликты частые и дорогие, и всё происходит внутри одной транзакции.
- **Что такое deadlock?** Две транзакции ждут блокировки друг друга. База одну убивает с ошибкой, код должен ретраить. Профилактика: брать блокировки в одинаковом порядке.
- **Почему мьютекс в Node не решает?** Инстансов сервера больше одного, они про мьютекс друг друга не знают. Решает база или общий lock в Redis.
- **Что такое last-write-wins?** Последняя запись перетирает предыдущую без проверки. Просто, но молча теряет чужие изменения.
