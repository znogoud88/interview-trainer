## Что это
**Коротко:** JOIN склеивает строки двух таблиц по условию: INNER оставляет только пары, у которых совпало, LEFT оставляет все строки левой таблицы и NULL вместо правой, если пары нет. GROUP BY сворачивает строки в группы и считает по ним (COUNT, SUM), HAVING фильтрует уже готовые группы. Foreign key это правило базы, что `orders.customer_id` обязан ссылаться на существующего клиента.

JOIN по механике: база берёт строку из `customers`, ищет в `orders` строки с таким `customer_id` и склеивает их в одну широкую строку. У клиента с тремя заказами будет три строки в результате, с данными клиента в каждой.
- `INNER JOIN`: клиенты без заказов пропадают, потому что склеивать не с чем.
- `LEFT JOIN`: клиенты без заказов остаются, в колонках заказа NULL. «Все клиенты, включая тех, кто ничего не купил» это всегда LEFT.
- `RIGHT JOIN` это LEFT наоборот, на практике переписывают в LEFT. `FULL OUTER JOIN` оставляет всё с обеих сторон.

GROUP BY и HAVING: `WHERE` отсеивает отдельные строки до группировки, `HAVING` отсеивает группы после. «Клиенты с более чем 5 заказами» нельзя написать через `WHERE COUNT(*) > 5`, потому что на момент WHERE счётчика ещё нет. В SELECT при GROUP BY можно только колонки из GROUP BY и агрегаты.

Foreign key: `orders.customer_id REFERENCES customers(id)`. База не даст вставить заказ с несуществующим клиентом и не даст просто так удалить клиента, у которого есть заказы. Что делать при удалении, выбираешь явно:
- `ON DELETE RESTRICT` (и `NO ACTION`, это дефолт): удаление клиента падает с ошибкой, пока есть заказы. Безопасный выбор по умолчанию.
- `ON DELETE CASCADE`: удаляются и заказы. Правильно для строк заказа при удалении заказа, опасно для клиента: один DELETE снёс всю историю.
- `ON DELETE SET NULL`: заказы остаются, `customer_id` становится NULL. Для необязательных связей: менеджер уволился, заявки остались без менеджера.

## Пример
```sql
-- все клиенты и количество их заказов, включая тех, у кого ноль
SELECT c.id, c.name, COUNT(o.id) AS orders_count
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;
-- с INNER JOIN клиенты без заказов просто исчезнут из результата

-- клиенты с более чем 5 заказами за этот год
SELECT customer_id, COUNT(*) AS cnt
FROM orders
WHERE created_at >= '2026-01-01'      -- фильтр строк до группировки
GROUP BY customer_id
HAVING COUNT(*) > 5;                  -- фильтр групп после
```

## Подводные камни
- `COUNT(*)` и `COUNT(o.id)` при LEFT JOIN разные: `COUNT(*)` посчитает строку с NULL как 1, и у клиента без заказов будет «1 заказ». `COUNT(колонка)` NULL пропускает.
- Условие на правую таблицу в WHERE превращает LEFT JOIN в INNER: `WHERE o.status = 'paid'` отбрасывает строки с NULL. Если нужны и клиенты без заказов, условие переносится в `ON`.
- JOIN на две связи «один ко многим» умножает строки: клиент с тремя заказами и двумя адресами даст шесть строк, и SUM по ним будет врать. Агрегировать по одной связи за раз или через подзапрос.
- «Целостность проверим в коде» это красный флаг: код с багом или ручной SQL в консоли обойдут проверку, FK в базе не обойти. Интервьюер хочет услышать, что CASCADE это осознанный выбор, а не дефолт.

## Вопросы вдогонку
- **Что вернёт LEFT JOIN, если справа нет совпадений?** Все строки левой таблицы, правые колонки NULL.
- **Можно ли написать WHERE COUNT(*) > 5?** Нет, агрегат считается после WHERE. Для этого HAVING.
- **Что будет при DELETE клиента с заказами и FK без ON DELETE?** Ошибка: по умолчанию NO ACTION, база не даст сломать ссылку.
- **Нужен ли индекс на колонку с foreign key?** Да, в Postgres он не создаётся автоматически. Без него JOIN и проверка при удалении родителя сканируют таблицу.
