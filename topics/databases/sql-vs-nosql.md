## Что это
**Коротко:** SQL (Postgres, MySQL) хранит данные в таблицах со строгой схемой и связями между ними и умеет транзакции: несколько изменений либо применились все, либо ни одно. NoSQL (Mongo) хранит документы: JSON-объект целиком, схема гибкая, данные легко раскидать по многим серверам. Зрелая позиция: по умолчанию Postgres, Mongo берём по конкретной причине, а не потому что модно.

Механика, а не определения:
- В SQL заказ это строка в `orders`, его клиент это строка в `customers`, их связывает `customer_id`. Данные не дублируются, а собираются JOIN'ом при чтении. База сама следит, что заказ не ссылается на несуществующего клиента (foreign key).
- В Mongo заказ это один документ `{ _id, customer: { name, address }, items: [...] }`. Читается одним запросом без JOIN, потому что всё, что нужно экрану, лежит рядом. Но если клиент поменял адрес, старые заказы об этом не узнают (для заказов это как раз правильно, для профиля нет).
- Транзакции на несколько документов в Mongo есть, но это не её сильная сторона. Там, где важна согласованность между сущностями (деньги, остатки, заказы), SQL проще и безопаснее.
- Горизонтальный скейл: Mongo с самого начала построена под шардирование (разные документы живут на разных серверах). Postgres шардируется, но руками и больно. Реально это нужно редко: один Postgres тянет очень много.

Embed vs reference в Mongo. Правило: что читается вместе, хранится вместе. Адрес доставки в заказе это embed: читается вместе с заказом, ограничен по размеру, не должен меняться задним числом. Комментарии к посту это reference, отдельная коллекция с `postId`: их может быть 10 тысяч, документ в Mongo ограничен 16 МБ, а бесконечно растущие массивы внутри документа это боль.

Many-to-many. В SQL это junction-таблица `student_courses (student_id, course_id)`, стандарт, JOIN в обе стороны. В Mongo это массивы id с обеих сторон (`student.courseIds`, `course.studentIds`), и синхронизировать их должен твой код: отписал студента, забыл обновить второй массив, данные разъехались, и никакой FK этого не поймает. Сильно связанные данные это аргумент за SQL.

## Пример
```sql
-- SQL: заказ и клиент хранятся отдельно, собираются при чтении
SELECT o.id, o.total, c.name
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.id = 42;
```
```js
// Mongo: заказ читается одним запросом, адрес лежит внутри (embed)
db.orders.findOne({ _id: 42 });
// { _id: 42, total: 1500, customer: { name: "Иван", address: "..." }, items: [...] }
```

Где Mongo оправдана: каталог товаров, где у разных категорий разный набор полей; логи и события (пишем много, схема плавает); контент CMS, который читается документом целиком.

## Подводные камни
- «NoSQL быстрее» это не ответ. Быстрее читать документ целиком, но медленнее и больнее собирать данные из нескольких коллекций: `$lookup` есть, но по удобству и скорости это не JOIN.
- Гибкая схема означает, что схему держит код. Через год в коллекции три формата одного документа, и каждый читатель должен уметь все три. Mongoose и schema validation в Mongo это признание, что схема всё-таки нужна.
- Postgres умеет JSONB: строгие таблицы плюс гибкое поле `attributes` для редких свойств. Часто это закрывает «нам нужна гибкость» без второй базы.
- Красный флаг на собесе: «Mongo для скейла» на проекте с 10 тысячами пользователей. Интервьюер хочет услышать про модель данных и паттерн чтения, а не про масштаб.

## Вопросы вдогонку
- **Mongo: embed или reference для комментариев к посту?** Reference: их много, растут бесконечно, читаются отдельно с пагинацией.
- **Как в Mongo сделать GROUP BY?** Aggregation pipeline: `$match`, `$group`, `$sort`, `$project`, конвейер этапов, каждый принимает результат предыдущего.
- **Транзакции в Mongo есть?** Есть, multi-document с версии 4.0. Но если они нужны постоянно, это намёк, что данные реляционные.
- **Почему many-to-many в Mongo больно?** Два массива ссылок надо обновлять синхронно вручную, и нет FK, который поймает рассинхрон.
