## Что это
**Коротко:** На живом проде старый и новый код какое-то время работают с одной базой одновременно: деплой катится поинстансно, минуту-другую половина серверов на старой версии. Поэтому каждая миграция должна быть совместима с обеими версиями кода. Паттерн называется expand-contract: сначала расширяем схему (добавляем новое, старое не трогаем), переключаем код, потом убираем старое.

Почему «переименовать колонку» одним шагом нельзя: `ALTER TABLE users RENAME COLUMN name TO full_name` отработает за миллисекунду, но старый код в этот момент делает `SELECT name` и падает. Накатить миграцию до деплоя: старый код сломан. После деплоя: новый код сломан, пока миграция не прошла. Никакой порядок не спасает, потому что оба живут одновременно.

Expand-contract на примере rename `name` в `full_name`:
1. **Expand.** Миграция: добавить `full_name` nullable. Старый код её не знает и не трогает, всё работает.
2. Деплой кода, который пишет в обе колонки, а читает из `full_name` с фолбэком на `name`.
3. **Backfill.** Перелить данные `UPDATE users SET full_name = name WHERE full_name IS NULL` батчами по 10 тысяч строк, не одним UPDATE на всю таблицу (он залочит таблицу и раздует WAL).
4. Деплой кода, который работает только с `full_name`.
5. **Contract.** Отдельная миграция, через день-два, когда точно ничего не откатится: `DROP COLUMN name`.

Каждый шаг обратим: если на шаге 2 что-то не так, откатываем код, колонка `full_name` просто лежит без дела. У миграции с данными план отката должен быть написан до запуска, а не после инцидента.

Что ещё ломает прод на больших таблицах:
- `ADD COLUMN ... NOT NULL` без default на заполненной таблице не пройдёт (нечем заполнить). С default в Postgres 11+ быстро, в старых версиях и в MySQL это переписывание всей таблицы под блокировкой.
- `CREATE INDEX` блокирует запись в таблицу на всё время построения. В Postgres есть `CREATE INDEX CONCURRENTLY`, в MySQL online DDL или pt-online-schema-change.
- Смена типа колонки (`int` в `bigint`): переписывание таблицы. Делается как rename: новая колонка, backfill, переключение, drop.

## Пример
```sql
-- ❌ одним шагом: старый код падает на SELECT name сразу после миграции
ALTER TABLE users RENAME COLUMN name TO full_name;

-- ✅ шаг 1 (expand): безопасно, старый код ничего не заметил
ALTER TABLE users ADD COLUMN full_name text;
-- ... деплой кода с двойной записью, backfill батчами, деплой кода только на full_name ...
-- ✅ шаг 5 (contract), через несколько дней отдельной миграцией
ALTER TABLE users DROP COLUMN name;
```

## Подводные камни
- Миграция, которая прошла локально за секунду, на проде с 50 млн строк идёт час и держит lock. Перед запуском смотреть, какую блокировку берёт DDL, и ставить `lock_timeout`, чтобы миграция упала, а не повесила прод.
- Миграция и код в одном деплое это иллюзия атомарности. Это всегда два отдельных шага, и у каждого свой откат.
- Откат миграции с `DROP COLUMN` невозможен: данные удалены. Поэтому contract откладывают и делают, когда новая версия точно прижилась.
- Интервьюер хочет услышать именно «старый и новый код живут одновременно» и шаги expand-contract. Красный флаг: «накатываем миграцию в окно обслуживания в три ночи» для продукта, у которого нет окна.

## Вопросы вдогонку
- **А если деплой атомарный, все инстансы разом?** Таких не бывает: даже blue-green переключает трафик, а in-flight запросы ещё доживают на старой версии.
- **Как добавить NOT NULL колонку на большой таблице?** Добавить nullable, backfill батчами, потом `ADD CONSTRAINT ... CHECK (col IS NOT NULL) NOT VALID`, отдельно `VALIDATE CONSTRAINT`, потом `SET NOT NULL`.
- **Куда девать миграции с данными (backfill)?** Отдельный скрипт или job, не в обычную schema-миграцию: та должна быть быстрой и идемпотентной.
- **Зачем таблица версий миграций в базе?** Таблица вроде `schema_migrations` фиксирует, что уже применено, чтобы на любом окружении миграции шли в одном порядке и не повторялись.
