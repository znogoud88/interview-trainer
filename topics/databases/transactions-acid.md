## Что это
**Коротко:** Транзакция это группа запросов, которая применяется как одно целое: либо все, либо ни один. Оформление заказа это три записи: создать заказ, уменьшить остаток товара, записать платёж. Если без транзакции упасть посередине, деньги списались, а заказа нет. С транзакцией база откатит всё до начала.

Механика: `BEGIN`, запросы, `COMMIT`. Если на любом шаге ошибка (или код сам сделал `ROLLBACK`), база возвращает данные в состояние до `BEGIN`. Пока транзакция не закоммичена, другие соединения её изменений не видят. Внутри базы это работает через журнал (WAL): сначала на диск пишется «что собираюсь сделать», потом сами данные, поэтому и откат, и восстановление после падения возможны.

ACID, концептуально:
- **Atomicity**: всё или ничего. То самое «заказ без платежа не бывает».
- **Consistency**: после транзакции данные соответствуют правилам базы (constraints, foreign keys, `CHECK (stock >= 0)`). Если правило нарушено, транзакция не коммитится.
- **Isolation**: параллельные транзакции не видят половинчатые результаты друг друга. Уровни изоляции (Read Committed по умолчанию в Postgres, Repeatable Read, Serializable) регулируют, насколько строго.
- **Durability**: что закоммичено, то не пропадёт при выключении питания, потому что уже лежит на диске в журнале.

С точки зрения фронтендера: транзакция это причина, почему один `POST /checkout` лучше трёх запросов `POST /orders`, `PATCH /stock`, `POST /payments`. Три HTTP-запроса из браузера в транзакцию не завернуть: если второй упал, первый уже применился.

## Пример
```js
// ❌ три независимых запроса: упал платёж, остаток уже списан, заказ висит
await db.order.create({ data: orderData });
await db.product.update({ where: { id }, data: { stock: { decrement: 1 } } });
await db.payment.create({ data: { amount: total } }); // кинул ошибку

// ✅ транзакция: либо всё, либо откат
await db.$transaction(async (tx) => {
  const order = await tx.order.create({ data: orderData });
  await tx.product.update({ where: { id }, data: { stock: { decrement: 1 } } });
  await tx.payment.create({ data: { orderId: order.id, amount: total } });
});
```

Внешний платёжный шлюз в транзакцию базы не входит: Stripe не откатится вместе с твоим ROLLBACK. Поэтому обычно так: транзакция создаёт заказ и резервирует остаток со статусом `pending`, потом зовём шлюз, потом вторая транзакция переводит заказ в `paid` или отменяет и возвращает остаток.

## Подводные камни
- Длинная транзакция держит блокировки и соединение из пула. Внутри транзакции нельзя ходить в сторонние API и ждать пользователя: пока она открыта, другие ждут.
- Транзакция защищает от падения посередине, но не от гонок сама по себе: два параллельных `SELECT stock` в двух транзакциях на Read Committed оба увидят 1. Для этого нужны блокировки или атомарный UPDATE, это отдельная тема.
- ORM молча оборачивает каждый отдельный запрос в свою транзакцию. «У нас ORM, у нас всё транзакционно» не так: три `await` подряд это три транзакции.
- Интервьюер хочет живой пример бага без транзакции, не расшифровку аббревиатуры. Красный флаг: ACID по буквам без понимания, что оно даёт на практике.

## Вопросы вдогонку
- **Что такое уровень изоляции?** Насколько одна транзакция видит изменения другой. Read Committed видит закоммиченное. Serializable: как будто транзакции шли по очереди, но дороже и бывают ошибки сериализации, которые надо ретраить.
- **Можно ли транзакцию через несколько сервисов?** Распределённые транзакции (2PC) тяжёлые и редкие. Обычно saga: цепочка локальных транзакций с компенсирующими действиями на откат.
- **Как база гарантирует durability?** Write-ahead log: запись в журнал на диск до ответа на COMMIT, при падении журнал проигрывается заново.
- **Что будет, если забыть COMMIT?** Транзакция висит открытой, держит блокировки и соединение, пока его не закроют по таймауту или не оборвётся клиент.
