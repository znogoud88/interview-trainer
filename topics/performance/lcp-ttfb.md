## Что это
**Коротко:** LCP 4.5s это зона «poor». Дебажить нужно системно: найти, какой элемент считается LCP, и пройти по цепочке: TTFB, потом когда браузер узнал о ресурсе и с каким приоритетом его грузит, потом размер и формат, потом время рендера. TTFB это время до первого байта HTML-ответа, и если он уже 2 секунды, LCP физически не может быть хорошим, сколько ни жми картинку.

LCP раскладывается на четыре фазы (так их показывает DevTools и web-vitals attribution):
1. **TTFB**: сервер думает + сеть + редиректы.
2. **Resource load delay**: от получения HTML до старта загрузки LCP-ресурса. Большая, если картинка обнаруживается поздно: подставляется через JS, лежит в CSS `background-image`, или на ней стоит `loading="lazy"`.
3. **Resource load time**: сама загрузка. Размер, формат, CDN.
4. **Element render delay**: ресурс есть, а отрисовать не можем: блокирующий JS/CSS, клиентский рендер, который ещё не отдал DOM.

Как найти LCP-элемент: Performance panel в DevTools, трек Timings, маркер LCP, клик показывает узел. Или PageSpeed Insights, блок «Largest Contentful Paint element». На продуктовой странице это почти всегда hero-картинка или фото товара.

TTFB: «хорошо» это примерно до 800ms. Лечение по месту:
- Сервер долго думает: медленные запросы к базе (N+1), SSR на каждый запрос без кеша. Кеш: ISR/SSG, CDN-кеш HTML, Redis для данных.
- Сеть: пользователь далеко от сервера. Edge, CDN, HTTP/2 или HTTP/3.
- Цепочки редиректов: http → https → www → /ru. Каждый это лишний round-trip, на мобильной сети по 200-300ms.

## Пример
```html
<!-- ❌ hero через CSS background и lazy: браузер узнаёт о картинке поздно и грузит с низким приоритетом -->
<div class="hero" style="background-image:url(hero.png)"></div>
<img src="product.png" loading="lazy">

<!-- ✅ обычный img, высокий приоритет, лёгкий формат, размеры -->
<link rel="preload" as="image" href="hero.avif" fetchpriority="high">
<img src="hero.avif" width="1200" height="600" fetchpriority="high" alt="...">
```
Разбор продукт-пейджа с LCP 4.5s по фазам: TTFB 1.8s (SSR ходит в базу без кеша; добавили кеш на 60s, стало 300ms). Load delay 1s (картинка была lazy и вставлялась JS-ом; вынесли в `<img>` с `fetchpriority`). Load time 1.2s (PNG 2 МБ стал AVIF 150 КБ через CDN с трансформациями). Итог около 1.6s. Порядок важен: чинить картинку при TTFB 2 секунды почти бесполезно.

## Подводные камни
- `loading="lazy"` на LCP-картинке это самая частая ошибка: браузер сознательно откладывает её. Lazy только ниже фолда.
- Картинка в `background-image` видна браузеру только после загрузки и применения CSS, preload scanner её не находит. Для hero лучше `<img>` или `<link rel="preload">`.
- Клиентский рендер (SPA): LCP ждёт, пока скачается бандл, выполнится, сходит в API, отрисует. Помогает SSR/SSG или хотя бы предзагрузка данных и критичного chunk.
- Высокий TTFB часто вообще не фронтовая проблема, но фронт первым её видит. Нужно уметь показать бэкенду цифры: Network panel (Waiting), `performance.getEntriesByType('navigation')[0].responseStart`.
- Интервьюер хочет услышать процесс (измерил, нашёл элемент, разложил по фазам, починил первое звено, перемерил), а не список трюков наугад.

## Вопросы вдогонку
- **Что может быть LCP-элементом?** `<img>`, постер `<video>`, элемент с `background-image`, блок текста. SVG-иконки и мелочь не считаются, берётся самый большой во viewport.
- **Как померить TTFB руками?** Network panel, колонка Waiting; `onTTFB` из web-vitals; `curl -w "%{time_starttransfer}"`.
- **LCP-элемент меняется между прогонами, это баг?** Нет, на разных viewport самый большой элемент разный. В lab фиксируй размер экрана, в поле смотри p75.
- **Поможет ли HTTP/3?** Сети да (меньше рукопожатий, лучше на потерях), серверу, который думает 1.5s над запросом, нет.
