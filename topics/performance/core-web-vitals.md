## Что это
**Коротко:** Core Web Vitals это три метрики от Google, которые показывают, насколько быстро, отзывчиво и стабильно работает страница для реального пользователя. LCP (< 2.5s) про загрузку главного контента, INP (< 200ms) про реакцию на действия, CLS (< 0.1) про то, что интерфейс не прыгает. Google учитывает их в ранжировании, поэтому бизнесу они тоже важны.

- **LCP, Largest Contentful Paint**: когда отрисовался самый большой элемент в первом экране: hero-баннер, картинка товара, крупный заголовок. Тормозят медленный сервер и API, тяжёлые картинки, блокирующий JS. Что улучшать: WebP/AVIF вместо jpeg/png, `srcset` чтобы браузер сам выбрал размер под экран и плотность пикселей, CDN (ближайший сервер + кеш + сжатие), меньше JS (defer/async, code splitting, tree shaking, не тащить lodash целиком). Lazy load только для того, что ниже фолда.
- **INP, Interaction to Next Paint**: сколько проходит от клика или нажатия до следующей перерисовки UI: клик по кнопке, обработчик отработал, браузер перерисовал. Считается по всем взаимодействиям за визит, берётся практически худшее. Тормозят тяжёлый JS, long tasks (большие синхронные циклы), лишние ререндеры. Что улучшать: разбивать задачи, debounce/throttle, меньше работы на одно действие.
- **CLS, Cumulative Layout Shift**: насколько «прыгает» интерфейс. Грузится картинка, и текст убегает; кнопка сместилась в момент клика, и нажал не туда. Это безразмерное число, не миллисекунды. Причины: картинки без размеров, динамические вставки. Что улучшать: `width`/`height` в атрибутах (браузер знает пропорцию и резервирует место), резервировать место под баннеры, не вставлять контент сверху.

INP заменил FID (First Input Delay) в марте 2024. FID мерил только задержку до старта обработчика первого ввода, INP смотрит на все взаимодействия и на полный цикл до отрисовки. Назвать FID актуальной метрикой это маркер устаревших знаний.

Пороги считаются по 75-му перцентилю (p75) пользователей. «Хорошо»: 2.5s / 200ms / 0.1. «Needs improvement»: до 4s / 500ms / 0.25. Дальше «poor».

## Пример
Где смотреть:
- **Lab**: Lighthouse в DevTools (Performance tab), PageSpeed Insights в нижней части. Синтетика: один прогон, одно устройство, фиксированный throttling. Воспроизводимо, поэтому удобно для отладки. Lighthouse не измеряет INP, потому что никто не кликает; вместо него там TBT (Total Blocking Time).
- **Field**: CrUX (Chrome User Experience Report) и свой RUM через библиотеку `web-vitals`. Данные реальных пользователей на их телефонах и сетях. Именно по field Google ранжирует.

```js
import { onLCP, onINP, onCLS } from 'web-vitals';
onLCP(console.log); onINP(console.log); onCLS(console.log);
```

Типичная история: на MacBook с гигабитом Lighthouse зелёный, а в CrUX LCP 4 секунды, потому что половина пользователей на Android за 100 долларов в 3G.

## Подводные камни
- Доверяем field, дебажим lab. Расхождение само по себе информация: у пользователей другие устройства, сети, кеш, размеры экранов.
- Lighthouse score это не Core Web Vitals. Score 95 ничего не гарантирует, смотри конкретные метрики и p75 в поле.
- CLS копится всё время жизни страницы, не только при загрузке. Попап, который сдвинул контент через минуту, тоже в счёт.
- В Next.js `next/image` сам делает srcset, современные форматы, размеры против CLS и `priority` для LCP-картинки, но это не повод не понимать, что под капотом.
- Красный флаг: назвать FID, не знать порогов, сказать «Lighthouse 100, значит всё хорошо».

## Вопросы вдогонку
- **Почему FID заменили на INP?** FID видел только задержку первого ввода, INP считает все взаимодействия и время до перерисовки, поэтому ловит тормоза, которые FID пропускал.
- **Что такое p75?** 75% пользователей должны уложиться в порог. Среднее прячет хвост медленных, p75 его показывает.
- **Какие метрики есть кроме трёх основных?** TTFB и FCP как диагностические, TBT в Lighthouse как lab-замена INP.
- **Что такое CDN одним предложением?** Сеть серверов по миру, отдаёт статику с ближайшего к пользователю, кеширует и сжимает (Cloudflare, CloudFront); вопрос цены и масштаба.
