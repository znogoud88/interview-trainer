## Что это
**Коротко:** Главный ручной тест доступности: пройти сайт без мыши. Tab идёт в логичном порядке, фокус всегда видно, всё интерактивное достижимо и срабатывает, фокус нигде не застревает. Модалка это место, где всё это ломается чаще всего: при открытии фокус уходит внутрь, пока она открыта, не выходит за её пределы, при закрытии возвращается на кнопку, которая её открыла.

Что проверять с клавиатуры:
- Tab / Shift+Tab идут как визуальный порядок. Порядок задаёт DOM, не CSS, поэтому `order` и `row-reverse` его ломают.
- Фокус видим. `outline: none` «потому что дизайнеру не нравится рамка» это зло: человек с клавиатуры не знает, где он. Свой стиль рисуем через `:focus-visible`: для мыши рамки нет, для клавиатуры есть.
- Всё достижимо: кастомные дропдауны, карточки-ссылки, иконки, меню, которое открывается только по hover.
- Нет ловушек: фокус зашёл в виджет (date picker, embed, редактор) и Tab оттуда не выводит. Это неумышленный focus trap, он плохой. Умышленный trap в модалке наоборот нужен.
- Enter активирует ссылки и кнопки, Space кнопки, стрелки работают внутри композитных виджетов (tabs, radio, menu).

Доступная модалка, чеклист:
1. При открытии фокус внутрь: на первый интерактивный элемент или на заголовок.
2. Focus trap: Tab с последнего элемента идёт на первый, Shift+Tab наоборот. Контент под модалкой недоступен (`inert` на остальном).
3. Esc закрывает.
4. При закрытии фокус возвращается на элемент, который её открыл. Это забывают чаще всего.
5. `role="dialog"`, `aria-modal="true"`, `aria-labelledby` на заголовок, `aria-describedby` на текст.
6. Скролл фона заблокирован.

## Пример
Нативный `<dialog>` делает почти всё сам:
```html
<button id="open">Удалить</button>
<dialog id="confirm" aria-labelledby="t">
  <h2 id="t">Удалить проект?</h2>
  <button id="cancel">Отмена</button>
  <button id="ok">Удалить</button>
</dialog>
<script>
  open.onclick = () => confirm.showModal();
  // showModal: фокус внутрь, Esc закрывает, остальная страница inert,
  // role=dialog и возврат фокуса при close браузер делает сам
</script>
```
Поддержка во всех современных браузерах с 2022. В React проще взять Radix Dialog / React Aria, они делают то же самое, если нативный не подходит.

## Подводные камни
- Глобальный `*:focus { outline: none }` в reset-стилях ломает клавиатуру на всём сайте. Замена: `:focus-visible { outline: 2px solid ...; outline-offset: 2px }`.
- Модалка через портал в конец body, а скринридер всё ещё может «уйти» в контент под ней курсором чтения. Поэтому `inert` на остальной разметке, одного `aria-modal` не всегда хватает.
- Возврат фокуса: если кнопку-источник удалили (удалили строку таблицы), возвращать фокус на соседний элемент или заголовок, иначе он улетает в body и Tab начинается сначала.
- `tabindex` больше нуля ломает естественный порядок, не использовать. Только `0` (добавить в порядок) и `-1` (фокусируемый программно, не через Tab).
- Skip link «Перейти к содержимому» первым в Tab-порядке, чтобы не протабывать 40 пунктов меню на каждой странице.
- Красный флаг: написать focus trap самому через `querySelectorAll` и забыть про возврат фокуса. Интервьюер хочет услышать про нативный `<dialog>` или библиотеку, и про возврат.

## Вопросы вдогонку
- **Чем `:focus` отличается от `:focus-visible`?** `:focus` срабатывает всегда, `:focus-visible` только когда браузер решил, что фокус нужно показать (клавиатура). Поэтому им стилизуют рамку без «рамки после клика мышью».
- **Что такое `inert`?** HTML-атрибут: поддерево нельзя сфокусировать и кликнуть, скринридер его не видит. Идеально для фона под модалкой.
- **Что такое roving tabindex?** Паттерн для композитных виджетов (tabs, toolbar): в Tab-порядке один элемент с `tabindex="0"`, остальные `-1`, внутри переключение стрелками.
- **Как сделать hover-меню доступным?** Открывать и по фокусу / Enter, закрывать по Esc, не прятать пункты через `display: none` так, что по Tab до них не дойти.
