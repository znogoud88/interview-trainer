## Что это
**Коротко:** Первое правило ARIA: не используй ARIA, если можно обойтись нативным HTML. `<button>`, `<a>`, `<nav>`, `<select>`, `<dialog>` доступны из коробки: фокус, клавиатура, роль и состояние для скринридера. Div с ARIA-атрибутами это попытка собрать то же самое руками, и почти всегда что-то забывают. Семантика даёт 80% доступности бесплатно.

Что `<button>` даёт бесплатно, а `<div onClick>` нет:
- Попадает в Tab-порядок (у div нужен `tabindex="0"`).
- Срабатывает по Enter и Space (у div нужен `onKeyDown` с проверкой обеих клавиш).
- Скринридер объявляет «кнопка» (у div нужен `role="button"`).
- `disabled`, `type="submit"` в форме, стили `:focus-visible` от браузера.
- Accessible name из текста внутри.

ARIA нужна там, где нативного элемента нет или он не умеет нужное:
- `aria-live` для объявления динамических изменений.
- `aria-expanded`, `aria-controls` у кнопки, которая открывает меню или аккордеон.
- `aria-label` у иконки-кнопки без текста.
- Роли сложных виджетов (tabs, tree, combobox), если нативный правда не подходит.

Главное про ARIA: она меняет только то, что слышит скринридер. Поведение (клавиатура, фокус) она не добавляет. `role="button"` на div не сделает его нажимаемым с клавиатуры.

## Пример
```jsx
// ❌ выглядит как кнопка, для скринридера и клавиатуры это просто текст
<div className="btn" onClick={save}>Сохранить</div>

// ❌ «починили» через ARIA, но Space не работает, а фокус не виден
<div role="button" tabIndex={0} onClick={save} onKeyDown={e => e.key === 'Enter' && save()}>
  Сохранить
</div>

// ✅ всё это уже внутри
<button type="button" onClick={save}>Сохранить</button>
```

Кастомный select это классическое минное поле. Нативный `<select>` умеет: открытие по Space/Enter, стрелки, поиск по первой букве, Esc, системный picker на мобильных. Кастомный «красивый дропдаун» на div должен воспроизвести всё это: `role="combobox"` или `listbox`, `aria-expanded`, `aria-activedescendant`, стрелки, Home/End, type-ahead, объявление выбранного. Combobox это один из самых сложных паттернов в ARIA APG. Взрослый ответ: сначала стилизуем нативный (хватает в большинстве случаев), кастомный берём из проверенной библиотеки (Radix, React Aria, Headless UI), а не пишем сами.

## Подводные камни
- Bad ARIA хуже, чем no ARIA: `role="button"` на ссылке, `aria-hidden="true"` на фокусируемом элементе, `aria-label`, который говорит другое слово, чем видимый текст. Скринридер верит ARIA и получает ложь.
- `<a>` без href не фокусируется. Ссылка ведёт на URL, кнопка делает действие. `<a href="#" onClick>` это кнопка, которая притворяется ссылкой.
- Landmarks (`<header>`, `<nav>`, `<main>`, `<footer>`) дают скринридеру навигацию по странице. Один `<main>` на страницу, у нескольких `<nav>` разные `aria-label`.
- Красный флаг: «делаем на div, потом добавим ARIA». Интервьюер хочет услышать «сначала нативный элемент, ARIA только там, где он не справляется».

## Вопросы вдогонку
- **Остальные правила ARIA?** Не менять нативную семантику (`<h2 role="tab">`), интерактивное должно работать с клавиатуры, не ставить `role="presentation"` или `aria-hidden` на фокусируемое, у каждого интерактивного элемента есть accessible name.
- **Откуда скринридер берёт имя кнопки?** Accessible name computation: `aria-labelledby`, потом `aria-label`, потом содержимое, потом `title`. Иконка без текста и без `aria-label` объявится как «кнопка» без имени.
- **Когда `role` всё-таки оправдан?** Виджеты без нативного аналога: tabs, tree, menu, slider с двумя ручками. И тогда брать паттерн из ARIA APG целиком, вместе с клавиатурой.
- **Чем `aria-label` отличается от `aria-labelledby`?** label это строка, labelledby это id элемента с текстом. labelledby приоритетнее и переводится вместе с контентом.
