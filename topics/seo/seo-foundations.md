## Что это
**Коротко:** SEO закладывается в архитектуру, а не прикручивается потом. С первого дня: важный контент приходит в HTML с сервера (SSR/SSG), у каждой страницы свои title/description/canonical, есть sitemap и robots.txt, человекочитаемые URL, правильные HTTP-статусы (404 это 404, переезд это 301). Главный риск SPA: краулер видит пустой `<div id="root">`, если контент появляется только после JS.

Как Google видит client-side rendered SPA:
- Googlebot исполняет JS (headless Chromium), но в два этапа: сначала скачивает и индексирует HTML, потом ставит страницу в очередь рендеринга. Очередь может занять от секунд до дней, бюджет рендера ограничен.
- Если контент зависит от медленного API, от скролла или от клика, рендер может его не дождаться.
- Другие краулеры (соцсети и мессенджеры для превью, многие AI-боты, часть поисковиков) JS не исполняют вообще. Пустой HTML = пустое OG-превью.
- Вывод: публичный контент, который должен ранжироваться (каталог, статьи, лендинги), рендерим на сервере. SPA за логином (кабинет, админка) краулеру не нужна, там CSR нормально.

Core Web Vitals и ранжирование: LCP, INP, CLS это ранжирующий фактор, но не главный. Google берёт field data из CrUX (реальные пользователи Chrome), а не Lighthouse. При равном контенте страница с хорошими CWV выше, плюс она лучше конвертит. Отчёт по CWV есть в Search Console.

JavaScript SEO, частые ловушки:
- Infinite scroll: краулер не скроллит, товары ниже первого экрана он не увидит. Решение: параллельно обычная пагинация ссылками `?page=2` с `<a href>`, и каждая страница пагинации отдаёт свой контент по URL.
- Ссылки только как `<a href="...">`. `<div onClick={() => router.push()}>` и `<a>` без href краулер не пройдёт, это тупик для обхода сайта.
- Контент в табах и аккордеонах, который рендерится только по клику, для краулера не существует. Если он нужен в индексе, рендерить сразу и прятать CSS.
- Lazy loading картинок через IntersectionObserver без `src` краулер может не загрузить, нативный `loading="lazy"` безопаснее.

## Пример
Проверка, что видит краулер, занимает минуту: `curl https://site.com/product/123 | grep "<h1"`. Если h1 нет, страница живёт только в JS. То же показывает Search Console, URL Inspection, «Test live URL» со скриншотом отрендеренной страницы.

```tsx
// ❌ контент приходит после маунта, в HTML его нет
useEffect(() => { fetch('/api/product/123').then(r => r.json()).then(setProduct) }, []);

// ✅ Next.js: данные на сервере, HTML уже с товаром и мета
export default async function Page({ params }) {
  const product = await getProduct(params.id);
  return <ProductView product={product} />;
}
export async function generateMetadata({ params }) {
  const product = await getProduct(params.id); // fetch дедуплицируется
  return { title: `${product.name} купить`, alternates: { canonical: `/product/${params.id}` } };
}
```

## Подводные камни
- «Google исполняет JS, значит всё нормально» это самый частый красный флаг. Исполняет, с задержкой, не всегда, и остальные не исполняют.
- SSR без правильных статусов: страница «не найдено» рендерится с кодом 200 (soft 404), краулер индексирует мусор. Статус должен приходить с сервера.
- Dynamic rendering (боту снапшот, людям SPA) работает, но Google сам называет это временным обходным путём, поддерживать дорого. SSR/SSG проще.
- Гидрация, которая меняет контент (другой title, другой текст), для Google выглядит как расхождение HTML и рендера, в Search Console это видно.
- Интервьюер хочет услышать: что рендерим где, чем проверяем, и что SEO это требование к архитектуре, а не задача маркетинга.

## Вопросы вдогонку
- **SSR, SSG, ISR: что выбрать для каталога?** SSG/ISR для стабильных страниц (категории, товары с редким обновлением), SSR для персонализированного или часто меняющегося. CSR только за логином.
- **Как проверить, что Googlebot видит страницу?** Search Console, URL Inspection с рендером; Rich Results Test показывает отрендеренный HTML; curl с UA Googlebot.
- **Что такое crawl budget?** Сколько страниц бот готов обойти за период. Для маленьких сайтов не проблема, для миллионного каталога критично: мусорные URL съедают бюджет.
- **Чем CWV из Lighthouse отличаются от Search Console?** Lighthouse это lab data с одного запуска, Search Console показывает field data из CrUX, и ранжирование смотрит на второе.
