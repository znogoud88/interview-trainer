## Что это
**Коротко:** Деплой без даунтайма это rolling (инстансы заменяются по одному) или blue-green (два полных окружения, трафик переключается). В обоих случаях старая и новая версия какое-то время живут вместе, и с одной базой, значит нужна совместимость версий. Feature flags разделяют deploy и release: код уже в проде, фича выключена, включаем постепенно и выключаем мгновенно без деплоя.

**Rolling**: из N реплик по одной (или по 25%) выводят из балансировщика, заменяют, возвращают. Дёшево, но минуту-другую в проде обе версии. **Blue-green**: рядом поднимается полная вторая среда (green), прогоняется смоук, переключается балансировщик. Откат это переключить обратно. Дороже по ресурсам. **Canary**: новая версия получает 1-5% трафика, смотрим метрики, расширяем.

**Миграции схемы** при совместимости: не ломать старый код. Expand/contract: сначала добавить колонку (старый код её игнорирует), выкатить новый код, потом удалить старую колонку отдельным релизом. `DROP COLUMN` одновременно с деплоем это ошибки на старых инстансах или даунтайм.

**Feature flags**: условие в коде, значение приходит из конфига или сервиса (LaunchDarkly, Unleash, свой). Даёт постепенный rollout (10% → 50% → 100%), включение по сегментам, kill switch. Делает возможным trunk-based development: мелкие PR в main каждый день, недоделанная фича под флагом. Gitflow с ветками релизов остаётся для версионируемых продуктов (mobile, SDK, on-prem).

**Деплой сломал прод, следующие 30 минут**: узнали из алертов, а не от пользователей → откат сразу, не дебаг под огнём → потом причина → post-mortem без виноватых → фикс плюс защита от повтора (тест, алерт, проверка в CI).

**Редизайн на живом продукте**: никакого big bang. Страница за страницей под флагом, старое и новое совместимы (общая навигация, общие данные), метрики на каждом шаге, откат всегда возможен.

## Пример
```tsx
// feature flag: deploy сделан, release решается отдельно
if (flags.isEnabled("new-checkout", { userId })) {
  return <NewCheckout />;
}
return <LegacyCheckout />;
```
Rollout: внутренние пользователи → 5% → 50% → 100%. Error rate вырос на 5%: флаг выключили, прод жив, деплой не нужен. Потом флаг и старый код удаляются.

## Подводные камни
- Фронт тоже страдает от совместимости версий: пользователь открыл страницу на старом бандле, а API уже новый, или чанк с хешем уже удалён с CDN (ChunkLoadError). Держать старые ассеты какое-то время, ловить ошибку загрузки чанка и перезагружать.
- Флаги копятся: через год сотня флагов, никто не знает, какие живые. Флаг это временное, с датой удаления.
- «Сначала найдём причину, потом откатим» это главная ошибка в инциденте. Rollback дешевле героизма.
- Откат с миграцией, которая уже удалила данные, невозможен. Поэтому expand/contract.
- Красный флаг на собесе: «у нас деплой в 3 ночи, чтобы никто не заметил».

## Вопросы вдогонку
- **Blue-green или rolling?** Blue-green даёт мгновенный откат и чистое переключение, но вдвое дороже по ресурсам. Rolling дёшево и по умолчанию в Kubernetes.
- **Чем feature flag отличается от A/B-теста?** Механика та же, цель разная: флаг про безопасный релиз, A/B про сравнение метрик у двух вариантов.
- **Что такое post-mortem?** Разбор инцидента: таймлайн, причина, почему не поймали, действия. Без поиска виноватых, иначе в следующий раз скроют.
- **Как откатить фронт на CDN?** Деплоить версии в отдельные папки и переключать указатель, не перезаписывать файлы. Откат это переключить назад.
