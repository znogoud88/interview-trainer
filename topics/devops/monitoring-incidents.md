## Что это
**Коротко:** Мониторинг это ошибки (Sentry), метрики (latency, error rate, ресурсы), логи и аптайм, плюс алерты на аномалии, чтобы узнавать о проблемах раньше пользователей. «Юзеры напишут в поддержку» означает, что мониторинга нет. Для дебага в распределённой системе нужны structured logging и correlation ID, который тянется через всю цепочку сервисов.

Четыре источника сигналов:
- **Ошибки**: Sentry или аналог ловит исключения с stack trace, source maps, release и user context. На фронте это JS-ошибки, unhandled rejections, ChunkLoadError.
- **Метрики**: error rate, latency (p50/p95/p99), throughput, CPU и память. На фронте ещё Core Web Vitals через RUM. Хранятся в Prometheus, CloudWatch, Datadog.
- **Логи**: structured (JSON с полями), а не `console.log("something happened")`. По ним ищут и агрегируют: Loki, ELK, CloudWatch Logs.
- **Аптайм**: внешняя проверка «сайт открывается» с нескольких точек мира.

**Алерты**: не на каждую ошибку, а на аномалии: error rate выше порога, p95 latency вырос, 5xx пошли после деплоя. Привязка к релизу: Sentry показывает, в какой версии ошибка появилась впервые.

**Correlation ID** (trace ID): генерируется на входе (фронт или gateway), передаётся в заголовке (`X-Request-Id`, `traceparent`) во все сервисы и пишется в каждый лог. По одному id собираешь всю цепочку: запрос с фронта → BFF → сервис → БД. Без него дебаг это поиск по времени и догадкам.

**Контейнер работает локально, падает в проде**: логи контейнера (`docker logs`, `kubectl logs --previous`), разница env (переменная не проброшена), лимиты памяти (OOM kill, exit code 137), права на файлы, сеть. `exec` внутрь, сравнить окружения. Классика: переменная не задана, и памяти отрезано меньше, чем Node хочет.

## Пример
После деплоя в 14:03 алерт «error rate 5xx > 2%». Смотрим Sentry: новая ошибка `TypeError: cannot read 'items' of undefined`, release 2.14.0, первая в 14:04. Откат, прод жив через 5 минут. Потом по correlation ID одного упавшего запроса идём в логи BFF: бэкенд вернул новый формат ответа без поля `items`, контракт поменяли без согласования. Фикс: защитный парсинг, контрактный тест, алерт остаётся.

Красный флаг на собесе: «узнали, когда пользователь написал в поддержку через два дня».

## Подводные камни
- Алерт на каждую ошибку: через неделю канал мьютят, и реальный инцидент тонет в шуме. Алерты только на то, на что нужно реагировать сейчас.
- Логи без структуры и без id: в проде их гигабайты, найти нужное невозможно. И они стоят денег.
- Sentry без source maps: stack trace в минифицированном бандле бесполезен. Заливать source maps на деплое.
- Фронтовые ошибки не мониторятся вообще: бэкенд зелёный, а у пользователей белый экран.
- Личные данные в логах и в Sentry (email, токены в URL): это и утечка, и проблема с compliance.

## Вопросы вдогонку
- **Что такое p95 latency и почему не среднее?** 95% запросов быстрее этого значения. Среднее скрывает хвост: 5% пользователей с ответом по 10 секунд.
- **Как передать correlation ID с фронта?** Сгенерировать id на запрос, положить в заголовок, логировать на всех хопах. Тогда ошибка в Sentry связана с логами бэкенда.
- **Что такое OOM kill?** Контейнер превысил лимит памяти, и его убило ядро или оркестратор, exit code 137. Лечится лимитом или `--max-old-space-size`.
- **Чем tracing отличается от логов?** Trace это дерево spans с временем каждого шага запроса (OpenTelemetry, Jaeger). Логи это события, trace показывает, где именно тормозит.
