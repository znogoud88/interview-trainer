## Что это
**Коротко:** Секреты (API-ключи, токены, пароли к БД) не лежат в репозитории: они живут в хранилище CI (GitHub Secrets, GitLab CI variables, Vault, AWS Secrets Manager) и подставляются в момент сборки или запуска. Второе важное различие: build-time переменные запекаются в бандл при сборке, runtime читаются при запуске. Для фронта это ловушка: `NEXT_PUBLIC_*` и `VITE_*` инлайнятся в JS и видны любому в браузере.

Две категории переменных:
- **Build-time**: бандлер заменяет `process.env.NEXT_PUBLIC_API_URL` на строку прямо в коде. Поменять без пересборки нельзя. Всё, что попало в бандл, публично: это не место для секретов.
- **Runtime**: читаются процессом при старте (`process.env.DATABASE_URL` на сервере). Можно менять конфигом без пересборки.

Принцип «один образ на все окружения»: артефакт собрали один раз, а на staging и prod подаётся разный конфиг снаружи. Если `API_URL` запечён в бандл, под каждое окружение нужна своя сборка, и то, что тестировали на staging, не то, что уехало в прод.

Как делать runtime-конфиг на фронте:
- SSR (Next.js): читать серверные `process.env` в runtime и отдавать клиенту через props или `/api/config`.
- Статический SPA: entrypoint контейнера генерирует `env.js` из переменных при старте, index.html подключает его до бандла, код читает `window.__ENV__`.

Хорошие практики: `.env.example` в репо с именами без значений, `.env` в `.gitignore`, секреты только в CI-хранилище с маскированием в логах, ротация ключей, разные ключи на окружения, least privilege для токенов CI.

## Пример
```js
// ❌ секрет с префиксом NEXT_PUBLIC_: уедет в бандл, виден в DevTools
NEXT_PUBLIC_STRIPE_SECRET_KEY=sk_live_...

// ✅ публичный ключ можно, секретный только на сервере
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_live_...   // ок, он и задуман публичным
STRIPE_SECRET_KEY=sk_live_...                     // только server-side, без префикса

// runtime-конфиг в статическом SPA
// docker-entrypoint.sh: echo "window.__ENV__={API_URL:'$API_URL'}" > /usr/share/nginx/html/env.js
const apiUrl = window.__ENV__.API_URL;            // один образ, разный env.js на staging и prod
```

## Подводные камни
- Утечка ключа в git: даже после удаления он остаётся в истории. Ключ ротировать, а не «удалить коммит». Боты сканируют GitHub за минуты.
- Секрет попал в логи CI через `echo $TOKEN` для дебага. Хранилища CI маскируют известные секреты, но не производные от них.
- `.env` закоммичен «временно». Классика инцидентов.
- Переменная не проброшена на окружение: локально всё работает, в контейнере `undefined`. Проверять при старте: fail fast с понятной ошибкой, а не падать на первом запросе.
- Красный флаг на собесе: не понимать, что `NEXT_PUBLIC_` или `VITE_` означает «публично». Или считать, что раз переменная в `.env`, то она секретна.

## Вопросы вдогонку
- **Почему переменная без префикса `NEXT_PUBLIC_` на клиенте `undefined`?** Next.js инлайнит в клиентский бандл только переменные с этим префиксом, остальные доступны лишь на сервере.
- **Как хранить секреты в проде, не в CI?** Secrets manager (Vault, AWS Secrets Manager, Azure Key Vault): сервис получает их по роли при старте, а не из файла.
- **Что такое `.env.example`?** Шаблон с именами переменных без значений, чтобы новый человек знал, что нужно задать.
- **Можно ли вообще хранить секрет на фронте?** Нет. Всё, что в браузере, публично. Секретные операции только через свой бэкенд или BFF.
