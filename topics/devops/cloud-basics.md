## Что это
**Коротко:** Фронтендеру или фулстеку достаточно ориентироваться в концепциях, а не знать все сервисы: object storage для файлов и статики, serverless-функции для кода по требованию, managed DB вместо своей, IAM-роли вместо ключей в коде. Концепции одни во всех облаках, меняются названия и консоль: S3 = Blob Storage = GCS, Lambda = Azure Functions = Cloud Functions, SQS = Service Bus = Pub/Sub.

**Object storage** (S3): файлы, картинки, бекапы, статика фронта с CDN сверху. **Presigned URL**: сервер по своим правам генерирует временную подписанную ссылку, и клиент грузит или качает файл напрямую в хранилище, минуя твой бэкенд. Классика для аплоада больших файлов: бэк не гоняет через себя гигабайты. Важно: права (только PUT, только этот ключ) и короткий срок жизни.

**Serverless** (Lambda): функция запускается по событию (HTTP, очередь, cron), платишь за время выполнения, а не за простой, масштабируется само. Минусы: cold start (первый вызов после простоя медленный, особенно с тяжёлым бандлом), лимиты времени и памяти, локальная разработка сложнее. Главная гоча: коннекты к БД. Тысяча параллельных функций это тысяча коннектов, Postgres столько не держит. Нужен пулер: RDS Proxy, PgBouncer или serverless-драйвер. И идемпотентность: функция может выполниться повторно (retry по событию), значит повтор не должен создать второй заказ.

**Managed DB** (RDS, Cloud SQL): бекапы, патчи, реплики, failover из коробки. Своя на VM дешевле по железу, но ты DBA в 3 ночи. Зрелый дефолт: managed, своя только по особой причине.

**IAM**: сервис получает права через роль или service account, а не через ключ в коде. Least privilege: Lambda, которая пишет в один bucket, имеет право только на `PutObject` в этот bucket. Ключ в репозитории это классика инцидентов: его находят за минуты и крутят майнинг за твой счёт.

Честная калибровка на «какие сервисы использовали»: «деплоился на S3 + CloudFront, писал Lambda для вебхуков, DB настраивал не я» звучит лучше, чем перечисление каталога AWS.

## Пример
Аплоад аватарки без прогона через бэкенд:
```ts
// бэкенд: по своей роли выдаёт временную ссылку только на PUT конкретного ключа
const url = await getSignedUrl(
  s3,
  new PutObjectCommand({ Bucket, Key: `avatars/${userId}.jpg`, ContentType: "image/jpeg" }),
  { expiresIn: 300 },
);
// фронт: грузит файл напрямую в S3, бэкенд трафик не видит
await fetch(url, { method: "PUT", body: file, headers: { "Content-Type": "image/jpeg" } });
// потом фронт сообщает бэкенду «готово», тот сохраняет ссылку в БД
```

## Подводные камни
- Presigned URL с долгим сроком жизни или без ограничения на тип и размер: любой зальёт что угодно. Короткий TTL, ограничения в подписи, проверка после загрузки.
- Публичный bucket «на время»: один из самых частых способов утечки данных.
- Lambda с `new PrismaClient()` внутри handler вместо уровня модуля: коннект на каждый вызов. Клиент создавать снаружи, чтобы переживал тёплые вызовы.
- Serverless «дешевле» только при неравномерной нагрузке. Постоянный высокий трафик дешевле на обычном сервере или контейнере.
- Красный флаг на собесе: «знаю AWS» без объяснения, что именно делал, или ключи в `.env` с полным доступом.

## Вопросы вдогонку
- **Что такое cold start и как уменьшить?** Инициализация окружения функции после простоя. Меньше бандл и зависимостей, provisioned concurrency, инициализация вне handler.
- **Как serverless работает с БД?** Через пулер (RDS Proxy, PgBouncer) или HTTP-драйвер (Neon, PlanetScale), иначе исчерпаешь коннекты.
- **Как отдать статический фронт из облака?** Bucket + CDN (CloudFront, Cloudflare), bucket не публичный, доступ только через CDN.
- **Зачем очередь между сервисами?** Принял запрос, положил в очередь, воркер разгребает: асинхронность и устойчивость к пикам. Доставка at-least-once, значит консьюмер идемпотентный, плюс DLQ для ядовитых сообщений.
