## Что это
**Коротко:** В TS типы совместимы по форме, а не по имени. Если у объекта есть все поля, которые требует интерфейс, он подходит, без `implements` и без наследования. Это duck typing, проверенный на компиляции. В Java/C# наоборот, номинальная типизация: два класса с одинаковыми полями это разные типы. Branded types это способ подделать номинальность там, где форма одинаковая, а смысл разный: `UserId` и `OrderId` оба `string`, но путать их нельзя.

Структурная типизация:
- `type Point = { x: number; y: number }`: любой объект с `x` и `y` это `Point`, даже если он `Vector3` с лишним `z`.
- Лишние поля не мешают при присваивании через переменную, но ловятся при передаче литерала напрямую (excess property check).
- Удобно для утиных контрактов (`{ length: number }` принимает и массив, и строку) и для моков в тестах: не нужно наследоваться от класса, достаточно повторить форму.
- Приватные поля класса ломают структурность: два класса с `private x` несовместимы, даже если поля одинаковые.

Branded types:
- `type UserId = string & { __brand: "UserId" }`: в рантайме это обычная строка, в типах отдельный тип, в который голый `string` не положить.
- Создаются в одном месте (парсер, валидатор, фабрика `toUserId(raw)`), дальше по коду бренд протаскивается бесплатно.
- Реальная польза в финтехе и доменах с кучей id: `getOrder(userId)` перестаёт компилироваться. То же для `Email`, `Cents` vs `Dollars`, `SanitizedHtml`.

`interface` vs `type` (кратко): почти взаимозаменяемы. `interface` умеет declaration merging, `type` умеет union, intersection, mapped и conditional. Выбор это консистентность в проекте, а не идеология.

## Пример
```ts
// структурно: Vector3 подходит там, где ждут Point
type Point = { x: number; y: number };
const v = { x: 1, y: 2, z: 3 };
const p: Point = v;                      // ok, лишний z не мешает
const p2: Point = { x: 1, y: 2, z: 3 };  // ошибка: литерал проверяется строже

// ❌ оба string, перепутать местами легко, компилятор молчит
function refund(userId: string, orderId: string) {}
refund(orderId, userId);

// ✅ branded: форма та же, тип другой
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };
const toUserId = (s: string) => s as UserId; // единственное место с as

function refund(user: UserId, order: OrderId) {}
refund(orderId, userId); // ошибка компиляции
```

## Подводные камни
- Структурность это и плюс, и источник багов: `{ id: string; name: string }` для `User` и `Product` взаимозаменяемы, пока формы совпадают. Там, где смысл важнее формы, бренд.
- Бренд живёт только в типах. `JSON.parse` или ответ API не станут `UserId` сами, нужен парсер на границе. Zod умеет `.brand<"UserId">()`.
- Брендить всё подряд это шум: каждый `string` через фабрику, каждая функция с кастом. Брендят то, что реально путают: id разных сущностей, деньги, единицы измерения, проверенные строки.
- `__brand` это поле-фантом, в рантайме его нет. Защиты в рантайме тоже нет, это только компилятор.
- Красный флаг на собесе: «TS как Java, типы нужно implements». Интервьюер хочет услышать «по форме», пример с лишним полем и понимание, зачем номинальность иногда нужна.

## Вопросы вдогонку
- **Почему мок через переменную принимается, а литерал нет?** Excess property check работает только для свежих литералов, которые присваиваются напрямую. Через переменную лишние поля разрешены.
- **Как бренд устроен в других языках?** В Rust/Haskell это newtype, в Java обёртка-класс. TS эмулирует через intersection с фантомным полем, потому что номинальных типов нет.
- **Можно ли сделать бренд без `as`?** Через `unique symbol` в качестве ключа или zod `.brand()`. Но где-то один `as` в фабрике всё равно будет, это нормально.
- **interface или type, что выберешь?** В проекте то, что уже принято. Если с нуля: `interface` для публичных объектных контрактов, которые могут расширяться, `type` для всего остального.
